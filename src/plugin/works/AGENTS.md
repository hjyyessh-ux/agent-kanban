# src/plugin/works/ — Works Settings, Summary & Completion Lifecycle

## Purpose

Backend for the Works tab's settings panel and the Work Summary pipeline. A `Work`
(see `src/core/work-store.ts`) groups one or more sessions; this directory owns
the `works.*` settings (independent of the wiki's LLM config) and the on-demand
LLM that turns a Work's connected-session transcripts into a 3–5 line Korean
summary, plus the completion lifecycle that turns "this Work is done" into a
bulk card done→archive sweep feeding the wiki pipeline. No background worker —
summaries are generated per Work on a button click
(`POST /api/works/:id/summary`) and the lifecycle runs inside
`PATCH /api/works/:id`, so there is nothing to start/stop.

| `work-lifecycle.ts` | `applyWorkPatch()` — the `PATCH /api/works/:id` body of work. On `status: 'done'` it selects every card of every linked session, **drops the favorited top-level ones** (`keptFavoriteCardIds`), refuses (`WorkCardsRunningError` → `409`) if any remaining seed has a live agent run, claims the sweep atomically (`workStore.claimArchiveSweep`), flips the non-`done` seeds to `done` under `Promise.allSettled`, and hands the survivors to `store.archiveCards()` (which stamps `wiki.status='pending'`). `works.done_confirm` defers the sweep until `confirmArchive: true`, and a Work parked in that state finishes on a confirmation-only patch (`isCompletionPatch`). `buildWorkCompletionPreview()` is the read-only counterpart behind `GET /api/works/:id/completion-preview`. `selectWorkCards()` / `resolveSessionStartedAt()` / `resolveWorkStartedAt()` are the pure helpers; `createWorkStartedAtResolver(cards)` wraps the last one into the `WorkStartedAtResolver` every link-set change hands to the store, and `loadWorkStartedAtResolver(store)` reads the snapshot for a caller that does not already hold one.<br><br>`reopenWork()` is the inverse of that completion, and the reason it lives here rather than in the store is that it spans both stores: it gathers the Work's archived card ids over the month-bounded read (`workCardScanFloor` + `timelineArchiveMonths` + `selectWorkCards`), calls `store.unarchiveCards()`, and **only then** writes `status: 'active'` / `archivedAt: null` / `supersededByWorkId: null`. ## For AI Agents

### Working In This Directory

- Works Summary reuses the wiki's one-shot LLM abstraction (`createWikiLlm`, `WikiLlmRunner`, `resolveWikiLlmRoute`) from `../wiki/wiki-llm.ts` and the transcript loader `loadClaudeTranscript` from `../wiki/wiki-transcript.ts`. The Summary **model is a separate setting** (`works.summary_model`) — never fall back to `wiki.model`. The route (codex vs claude) is derived from the model prefix, so only the model id is persisted (no separate runtime key).
- `generateWorkSummary` takes the runner + transcripts as injected deps and does no I/O itself — keep it pure so it stays unit-testable without spawning a CLI (`src/__tests__/works-config.test.ts` injects a fake runner). The route in `src/server/routes.ts` builds the real runner, resolves each session's transcript from the board cards (session → card → `agentRuntime`/`projectDir`), persists the result via `workStore.updateWork({ summary })`, and returns a `WorkSummaryResponse`.
- **`min()` is resolved inside the store's lock, by every writer.** The route reads one archive-inclusive card snapshot per request, wraps it in `createWorkStartedAtResolver(cards)`, and hands that to `addSession` / `removeSession` / `moveSession` / `pruneMissingSessions`; each runs it against the link set its own write just produced. Computing the date in the route first (what `resolveWorkStartedAtAfterLinkChange` used to do) is a TOCTOU — two concurrent links each resolved `min()` over a set that did not contain the other session, and the later write won. It also re-read the whole archive per link: assigning 20 sessions was 20+ full scans. Do not reintroduce a pre-computed `startedAt` on `AddWorkSessionInput`.
- The link path adopts subagent sessions: `POST /api/works/:id/sessions` links the requested session **and its `parentCardId` descendants** (`linkSessionWithSubagents` in `src/server/routes.ts`, tree in `src/core/session-chain.ts`), one resolver call per link — a batch does not get to skip the `min()` recalculation, it only shares the snapshot. Sessions already linked elsewhere are skipped, so the store's 1:N invariant stays the only authority.
- `POST /api/works/:id/sessions/batch` is the multi-select verb. Same rules per session; one snapshot for the whole call; **partial failure is a response field (`failed[]`), not an exception** — 1:N is per session, so one `409` must not roll back the links that landed. `linkSessionWithSubagents(..., { cards })` is how the snapshot is threaded through.
- Dangling links live in `work-links.ts`, not here. The rule that matters: **a link is stamped, never auto-removed.** Card deletion is a soft delete that `restoreCard` reverses, and a session with no cards is filtered out of the Inbox — so auto-unlinking would turn a reversible action into an unrecoverable one. Removal is `WorkStore.pruneMissingSessions` behind a confirmed button, and it keeps a Work it empties (unlike `moveSession`, which deletes an emptied source because that move is a merge with a destination).
- Route ordering matters: `GET/POST /api/works/config` must be registered **before** the `/^\/api\/works\/([^/]+)$/` catch-all (otherwise `config` is parsed as a Work id). There is a regression test for this.
- `applyWorkPatch` is the **only** place card-level completion side effects belong. The hard rules, all regression-tested in `src/__tests__/work-lifecycle.test.ts`:
  1. Never call `store.archiveCards([])` — an empty seed list means "archive every done card on the board", so a Work with no linked cards must short-circuit to `archiveSkipped='no-cards'` (and stay un-stamped, so it is completable once its sessions produce cards).
  2. Card status changes go through the plain `store.updateCard` write, never a completion hook, so bulk-closing a Work cannot trigger queue auto-dispatch.
  3. **A card with a live runtime run blocks the whole transition.** Throw `WorkCardsRunningError` *before* recording anything: archiving a card out from under its runtime makes the completion hook fail with `Card not found` and hands the wiki an unfinished transcript. The verdict comes from the injected `ActiveRunProbe` — keep the `RuntimeRunStore` out of this file so the lifecycle stays unit-testable.
  4. **The idempotence guard must be atomic.** `claimArchiveSweep` decides and stamps in one lock; do not go back to `getWork` + `updateWork`, which let two concurrent `done` patches both sweep. Because the stamp now leads, a sweep that archives **nothing** must roll `archivedAt` back — that is what keeps the "never advertise an archive that did not happen" invariant.
  5. **Report partial sweeps.** Card writes settle independently (`Promise.allSettled`) and failures go out as `failedCards` → the response's `sweep.failed[]`. Do not let one card's rejection escape as a failure of the patch: it used to surface as `404 Work not found`.
  6. A confirmation-deferred Work (`status='done'`, no `archivedAt`) is finishable by a patch carrying only `confirmArchive: true`. `isCompletionPatch` is what recognizes it; classifying that shape as `not-a-completion` made the deferred state a dead end.
  7. **Favorited top-level cards are not swept and not flipped.** `favorite` means "pin to the board"; `store.archiveCards` already honours it for cascaded children, and this was the one path that supplied its own seeds and walked past it. Flipping them `done` without archiving is not a compromise — the next plain `archiveCards()` (no ids = every `done` card) would take them. Report via `keptFavoriteCardIds`, and end `favorites-only` **un-stamped** when that is all there is, so un-starring makes the Work completable again. Keep the filter here, not in `store.archiveCards`, so `POST /api/archive` is unchanged.

  Read `docs/invariants.md` → "Work 완료 라이프사이클" before touching this file.
- `discarded` is deliberately cheap: resolution stamps only, no card mutation. `WikiWorker` drops the Work from its **grouping index** and nothing more — those sessions fall back to per-session grouping and run the ordinary wiki flow, so a discarded Work never flips a card's wiki state. Do not add an archive step (or a wiki skip) to the discard path — the Timeline needs the cards to stay put, and `scripts/wiki-requeue-discarded.ts` exists to re-queue cards that the older skip behaviour retired.
- Transcript loading is Claude-only and best-effort; a Work whose sessions have no readable transcript returns `422` ("No session transcripts available"), never a fabricated summary.

## Review fixes (2026-09-08)

- Completion scope includes the actual `parentCardId` cascade, even for child sessions created after assignment. Use `selectWorkSweepCards` / `selectArchiveCards` for preview and guards. Explicit ownership by another Work blocks the transition.
- `archiveCards` runs the Work guard under the board lock immediately before writes. A late run or changed target set leaves a reported, retryable batch failure (successful earlier card flips remain, archive stamp is cleared).
- Work Summary falls back to saved card prompts/results when native transcripts are unavailable and reports `cardSourceSessions` separately from skipped sessions.
