# src/server/ — Bun HTTP Server and Routes

## Purpose

Thin Bun server layer. `index.ts` owns `Bun.serve()` and SPA/static serving; `routes.ts` (a hot-path file, 124+ edits) owns all REST endpoints for cards, schedulers, settings, scripts, screenshots, models, pending questions, wiki, and the scope manager (`/api/scope/*`: targets, inventory, cold storage freeze/restore/detail).

## Key Files

| File | Description |
|------|-------------|
| `index.ts` | `createServer()` wraps `Bun.serve()`, port-retry (configured port + 3), SPA static/HTML-fallback serving, API-first routing before static lookup |
| `routes.ts` | All REST endpoints — cards/archive/dispatch, Quick Actions, schedulers, settings, scripts, skills, skill-roots, models, questions, wiki proxy, and runtime-aware `/api/scope/*` (targets, MCP inventory/write, cold freeze/restore/detail) |
| `maintenance-runner.ts` | Update/restart maintenance flow backing `/api/maintenance/*` routes |

## For AI Agents

### Working In This Directory

- `createServer()` in `index.ts` takes a long positional-argument list of optional stores/fns (dispatch, scheduler, settings, script, models, question-monitor, aggregate/local-peer session fns, peer-token fn, runtime-catalog fn, wiki-worker, skill store, skill-roots store, placement-targets store, scope-MCP inventory fn, quick-action store, script-execution service, work store) — when adding a new store dependency, extend this list and thread it through `createRouteHandler()` in `routes.ts` rather than reaching for a global.
- Session aggregation lives in the exported `computeSessionAggregates(store, aggregateSessionsFn)` helper (`routes.ts`) so `GET /api/sessions` and `GET /api/works/inbox` share one view; add fields there, not inline in a route. It has **two** aggregation paths (card-derived and native `aggregateSessionsFn`) — an enrichment that only lands on one of them silently disappears depending on deployment, so derive it once above the branch, the way `relatedSessionIds` (`buildSessionChainMap`), `parentSessionIds` (`subagentAncestorSessions`) and `sessionKind` are. They need the archived cards the helper already loads; recomputing them on the web side would see only board cards and under-report.
- **`plugin/bootstrap.ts` always injects `aggregateSessionsFn`, so the native path is the only one production takes** — the card-derived path exists for unit tests and a plugin-less server. A route test that leaves the aggregator `undefined` therefore proves nothing about production. `relatedSessionIds` was written inside the card-only branch and passed every test while being permanently `undefined` in the daemon: the chain map was recomputed every 10s poll and thrown away, so `🔗 이어진 세션` never once fired for a real user. Cover both paths (`src/__tests__/works-inbox-route.test.ts` wires the aggregator).
- `GET /api/works/inbox?since=&limit=` is a **bounded** triage queue, not a session archive. Four things are filtered out in the route: linked/ignored sessions; sessions with **no card at all** (a peer runtime reports every session it has open, and `(No linked card)` rows used to accumulate without limit and keep the Works tab badge permanently lit); subagent sessions whose parent is already assigned (the parent's Work owns them); and anything outside the `since` window (default 30 days) beyond `limit` (default 200, cap 1000). Query parsing is the pure exported `parseInboxQuery(params, now)` — a bare number always means *days*, because `Date.parse('30')` is a year in some engines. A session with a running card is kept regardless of the window. The four filters themselves are the exported predicate `isInboxTriageMaterial(session, ctx)` and the row DTO is `toInboxSession(session)`, both shared with `GET /api/works/ignored-sessions` — that route has to answer "would restoring this actually bring the row back?", and the only honest answer is the Inbox's own rule.
- `POST /api/works/:id/sessions` links the requested session **plus its subagent descendants** (`linkSessionWithSubagents`): a subagent session is not independent work, so once the parent has a Work its children do too. Descendants already linked elsewhere are skipped — the 1:N invariant is the store's and this must never become a way around it. The response is `WorkAddSessionResponse` = the `Work` plus `cascadedSessionIds`, a superset for the same reason `WorkPatchResponse` is. `POST /api/works/reconcile-subagents` is the idempotent one-shot for Works linked before this existed; it must stay registered before the `/api/works/:id` catch-all.
- That link route also **requires an `active` target** (`WorkNotActiveError` → `409`): a `done` Work has already handed its cards to the wiki pipeline and a `discarded` one exists only to release its sessions. The gate is `linkSessionWithSubagents(..., { requireActive: true })`, so `reconcile-subagents` (data repair over historical Works of any status) is exempt — and so is a **re-link of a session the Work already holds**, which is how the `⋯` menu edits a link's role and changes no grouping. The client filters recommendations to active Works, but a panel can sit open across a status change (Works polls every 10s), so the server re-checks.
- `GET /api/works/ignored-sessions` / `DELETE /api/works/ignore-session/:sessionId` are the read and undo sides of `POST /api/works/ignore-session`, which had neither: `ignoredSessionIds` was append-only and unreadable over HTTP, so one `폐기` removed a session from the Inbox, the tab badge and the Timeline permanently. Both are literal-segment paths and must stay ahead of the `/api/works/:id` catch-all. The DELETE answers `404` for an id that was not on the list rather than reporting a no-op as success.
- `GET /api/works?status=&projectDir=&q=&sort=` applies the pure `selectWorks()` (`src/core/work-list.ts`) — the **same function the web Active list uses**, so the route and the screen cannot disagree on what "stale" or a search hit means. An unknown `sort` is `400 Invalid sort`, not a quiet fall back to the default order. `projectDir` is an exact match.
- `POST /api/works/:id/reopen` and `POST /api/works/:id/merge` are three-segment literals and must stay registered **before** the `/^\/api\/works\/([^/]+)$/` catch-all, same rule as `/api/works/config`. Reopen exists because completion was a one-way door: `PATCH` accepted `status: 'active'` but the archived cards never came back and `archivedAt` stayed stamped, which kept the sweep guard *and* the session-move gate shut for good — the only escape was `DELETE`, i.e. discarding the record. It restores the cards (`store.unarchiveCards`) **before** the status write, so a failed restore cannot leave an `active` Work whose cards are still archived. `409` when already active. Merge folds one Work's sessions into another and **keeps the source** as `discarded`/`superseded`/`supersededByWorkId`; it takes `await loadWorkStartedAtResolver(store)` so the target's `min()` runs inside the store lock like every other link-set change. Neither route may grow a queue/dispatch side effect — reopening work must not start an agent.
- `PATCH /api/works/:id` type-checks every field before the store sees it, and **refuses `archivedAt`, `wikiDocPath` and `supersededByWorkId` outright** (`400`) — both are server-owned (`claimArchiveSweep` / `WikiWorker`), and `archivedAt` gates the sweep's idempotence *and* the session-move rule, so a client string parked there froze both with no UI to undo it. Dates are normalized with `new Date(v).toISOString()` so mixed offsets cannot be compared as text downstream. `{"title": 7}` answers `400 title must be a string`, not `400 .trim is not a function`. `resolution: 'superseded'` is also `400`: only the merge route stamps it, and only together with the `supersededByWorkId` that says where the sessions went — one half alone is a 병합됨 Work pointing nowhere. `notes` is validated as `string | null` with a `WORK_NOTES_MAX_LENGTH` cap, and a violation stores nothing.
- `PATCH /api/works/:id` is not a plain store write: it goes through `applyWorkPatch()` (`src/plugin/works/work-lifecycle.ts`), which on `status: 'done'` flips every card of every linked session to `done` and archives them (handing them to the wiki pipeline). `works.done_confirm` (**default `true`**) gates that sweep behind a `confirmArchive: true` body flag — **do not add a second endpoint for it**; the Works UI calls this one path. The settings-unavailable fallback is `true`, not `false`: an unreadable setting must not open the destructive path. `status: 'discarded'` records the resolution only. See `docs/invariants.md` → "Work 완료 라이프사이클".
- The route injects `activeRunProbe` into `applyWorkPatch` — one `runtimeRunStore.listRuns()` read that answers "which of these cards has a live agent run". A `done` transition with any running card is refused `409 { error, runningCardIds }`; the lifecycle stays store-agnostic behind the `ActiveRunProbe` type. Without a run store the probe is `undefined` and the guard stands down (tests only — the server always wires it).
- The `PATCH /api/works/:id` response is `WorkPatchResponse` = the `Work` **plus** a `sweep` report (`archivedCount`, `archiveMonth`, `skipped`, `failed[]`, `keptFavoriteCardIds`). It is a superset of `Work` rather than a `{ work, sweep }` envelope so existing callers are untouched. Keep reporting `sweep.failed[]` — the sweep is N independent card writes and partial success is a real outcome; swallowing it is what made a half-archived Work look like a clean completion.
- Every Works route catch classifies on the error **class** (`src/core/work-errors.ts`) via the shared `worksErrorResponse()`, not on the message. The substring mapping it replaced (`message.includes('not found')` → `404 Work not found`) reported a Work that existed — with most of its cards already archived — as missing, because one card had vanished mid-sweep.
- `GET /api/works/:id/completion-preview` backs the completion confirmation dialog: archive-inclusive card counts (same `workCardScanFloor` + `timelineArchiveMonths` month selection as `/sessions`) plus the running-card list. Favorited board cards are counted out of `sweepCardCount` into `favoriteCardIds`, and excluded from the running-card probe, because the sweep leaves them alone — the dialog must promise exactly what the sweep will do. Pure aggregation in `buildWorkCompletionPreview` (`src/plugin/works/work-lifecycle.ts`) — read-only, so do not give it side effects, and do not switch it to `store.loadArchives()`.
- A `PATCH /api/works/:id` carrying only `startedAt`/`resolvedAt` is the date-edit path (Timeline bar-edge drag, Work detail date inputs). It skips every completion side effect because `status` is absent; the route rejects unparseable timestamps and the store rejects an edit that would put `resolvedAt` before `startedAt`.
- **Every route that changes a Work's link set hands the store a resolver, never a date.** The route reads one archive-inclusive card snapshot per request, wraps it in `createWorkStartedAtResolver(cards)` (or `loadWorkStartedAtResolver(store)` when it holds no snapshot yet), and `WorkStore.addSession` / `removeSession` / `moveSession` / `pruneMissingSessions` run it *inside their own lock* against the link set they just wrote. Resolving in the route first (the old `resolveWorkStartedAtAfterLinkChange`) was a TOCTOU — two concurrent links each answered `min()` from a set without the other session and the later write won — and re-scanned the whole archive per link, so a 20-session assignment was 20+ full scans. `AddWorkSessionInput` deliberately has no `startedAt` field any more.
- `POST /api/works/:id/sessions/batch` is the multi-select verb, registered **before** the two-segment `/sessions` route. One snapshot for the whole batch (threaded into `linkSessionWithSubagents(..., { cards })`), and **partial failure is a response field** (`failed[]`), not an exception: the 1:N invariant is per session, so one `409` must not undo the links that landed.
- `DELETE /api/works/:id/sessions/:sessionId` is a **no-op that writes nothing** when the Work does not hold that session — no recalculation, no `updatedAt`. It used to recalculate regardless, so a redundant DELETE overwrote a manually dragged `startedAt` with a derived value. Its catch goes through `worksErrorResponse` like every other Works route; the old blanket `500 Failed to remove session` hid which rejection had happened.
- `POST /api/works/reconcile-links` and `POST /api/works/:id/prune-sessions` are the dangling-link pair (`plugin/works/work-links.ts`). Card deletion never told Works anything, so a session whose cards were all deleted stayed linked and `resolveWorkStartedAt` fell back to its `linkedAt` — the Timeline bar started at triage time. `DELETE /api/cards/:id` and `POST /api/cards/:id/restore` now call the shared `reconcileWorkLinkForCard()` narrowed to the one owning Work, best-effort so bookkeeping can never fail a card write; `bootstrap.ts` runs the whole-store pass once at boot. **The reconcile only stamps `cardsMissingAt`** — removal is the user's explicit `prune-sessions`, because card deletion is a soft delete and a card-less session does not reappear in the Inbox.
- `PATCH /api/works/sessions/:sessionId` moves a session's link to another Work (`workStore.moveSession`). Its literal `sessions` segment means it must be registered **before** the `/^\/api\/works\/([^/]+)$/` catch-all, same rule as `/api/works/config`, and it must not be confused with `DELETE /api/works/:id/sessions/:sessionId` (Work id in the second segment there, the literal `sessions` here). The route reads the card snapshot once and hands `resolveWorkStartedAt` to the store as a resolver; the completing/archived-Work gate and the min() both run inside the store lock, because the move dialog can sit open across a status change.
- `GET /api/works/:id/sessions` backs the Work detail dialog. It is the **only** other route that reads the archive by month, and it composes the Timeline's own helpers to do it: `workCardScanFloor(work)` picks the window start, `timelineArchiveMonths` picks the months, `buildWorkSessionsResponse` (all three in `src/core/timeline-aggregate.ts`) does the aggregation. It exists because completing a Work bulk-archives every card under it — a client-side rollup off `/api/cards` reports `카드 0 · done 0` for exactly the Works whose purpose is to be reviewed. Do not switch it to `store.loadArchives()`, and do not move the aggregation into the route.
- `GET /api/cards/:id?include_archived=true` and `GET /api/cards?session_id=&include_archived=true` are the deep-link reads behind that same dialog and the Timeline: a card detail for an archived card, and a whole session's cards for the conversation modal. Without them a Timeline day cell or a completed Work's `대화` button hit `404`/an empty list and failed silently. The single-card path uses `store.getCard(id, { includeArchived: true })` (month-by-month, first hit wins); `session_id` is a filter over the already-loaded result, not a new scan.
- `GET /api/timeline?from=&to=&subagents=` backs the Board tab's Timeline view. It reads the card archive by month (the only other route that does is `GET /api/works/:id/sessions`, which reuses these same helpers): it composes `store.listArchiveMonths()` + `store.loadArchiveMonth()` (month selection in the pure `timelineArchiveMonths`, aggregation in `buildTimelineSessions` — both in `src/core/timeline-aggregate.ts`), and must never be switched to `store.loadArchives()`, which is the full-archive scan the wiki and Telegram paths rely on. `from`/`to` are required and validated by the pure `checkTimelineWindow`, which also **caps the window at `TIMELINE_MAX_WINDOW_DAYS` (400)**: the window is the only bound on the read and this is an unauthenticated GET, so `from=1970&to=2030` used to parse every archive month on disk in one request. Keep the validation in that function rather than inlining it here, and do not add an unwindowed variant. The response carries **no** Work grouping on purpose — the web client already polls `/api/works` and maps session → Work itself, which keeps an optimistic assignment from waiting on a refetch. It *does* read the Work store for one thing: `ignoredSessionIds`, passed to `buildTimelineSessions` so a discarded session comes back `ignored: true`. It keeps its row (the work ran) but loses its 배정 button, which pointed at an Inbox entry that no longer existed and was inert forever.
- `/api/*` routes are handled before any static asset lookup (see `index.ts` `fetchHandler`).
- Parameterized routes use manual regex/string matching (`path.startsWith(...)`, `path.endsWith(...)`) — there is no router library.
- Success responses are JSON; failures always use `{ error: string }`.
- If `staticDir` is missing, the server still works in API-only mode (used by tests).
- `routes.ts` is large (~98KB) and edited frequently — grep for the exact `method === 'X' && path === 'Y'` block before adding a new one nearby, and follow the existing block shape (auth classification, JSON parse, store call, response).

### Common Patterns

- Classify every new route in `requiresLocalAuth(method, path)`: mutating methods plus secret/script/scope reads must require the bearer token; read-only, non-secret routes may skip it.
- Never echo unmasked secret values from list/bulk responses — only single-entry, token-protected reads may return plaintext (see `GET /api/settings/:id`).
- Reuse `plugin/wiki/wiki-worker.ts`, `core/cold-storage-store.ts`, `core/mcp-runtime-adapter.ts`, `core/mcp-config-store.ts`, `core/codex-mcp-config.ts`, and `core/placement-targets-store.ts` for scope/wiki business logic instead of inlining it in `routes.ts`.
- Missing MCP `runtime` in legacy request bodies means `claude`; validate explicit values as `claude | codex`, use runtime + name for inventory identity, and placement identity for exact writes. Preview requests must not mutate files.
- `/api/scope/inventory` keeps the legacy Claude `ContextDiagnostics` counts Claude-only and adds Codex scan/trust diagnostics under `diagnostics.mcpDiscovery`.

## SECURITY MODEL

The SPA is served same-origin, so the API grants **no cross-origin access**:

- **No wildcard CORS.** Responses carry no `Access-Control-Allow-Origin`. Do not re-add `*`.
- **Same-origin guard** (`isForbiddenCrossOrigin`): any request whose `Origin` host differs from the `Host` is rejected `403`. This is the primary CSRF / drive-by defense and works for both `127.0.0.1` and `network_exposed` (LAN) binds. Non-browser clients send no `Origin` and pass.
- **Local token auth** (`requiresLocalAuth`): when a token is configured (`peerTokenFn`, wired by the plugin/daemon), all mutating methods plus secret/script/scope reads require `Authorization: Bearer <token>`. When no token is wired (unit/e2e test servers) the gate is a no-op and the same-origin guard remains active. Currently gated path prefixes include `/api/settings`, `/api/scripts`, `/api/skills`, `/api/skill-roots`, and `/api/scope`.
- **Token bootstrap** `GET /api/auth/token`: returns the token to **loopback clients only**, so remote devices under `network_exposed` cannot obtain it (and thus cannot mutate or read secrets). The SPA fetches it on boot (`web/src/api/authFetch.ts`).
- **Secret redaction**: `GET /api/settings` (list) and settings write responses redact masked values (`value: ''`). Plaintext is only returned by the explicit, token-protected single-entry `GET /api/settings/:id`. The scope manager applies the same discipline via `detectPlaintextSecret` (`core/mcp-config-store.ts`) and `secret-detect.ts` before surfacing MCP config values.

When adding routes: classify them in `requiresLocalAuth` (mutations and secret/code/scope reads need auth) and never echo masked secret values in bulk responses.

Prompt Quick Action runs validate stored definitions and directories before atomically creating a card, then call the injected shared `dispatchFn`. Script Quick Actions and `/api/scripts/:id/run` both call the injected `ScriptExecutionService`; never add route-local spawn or shell selection.

Quick Action create/update routes surface the shared icon validation messages. Duplicate icons and exhausted automatic palette claims are conflicts (`409`); malformed custom emoji are invalid requests (`400`).

## ANTI-PATTERNS

- Express/Hono/Koa or middleware chains
- Response shapes that drift from `{ error: string }`
- Re-introducing wildcard CORS, or skipping the same-origin guard / auth classification on new endpoints
- Returning plaintext masked secrets from list or write responses
- Hiding route-side business logic outside `routes.ts` without a clear shared helper

## NOTES

- `index.ts` reads SPA files into `ArrayBuffer` first to avoid Bun header/body race issues on non-loopback interfaces.
- `routes.ts` also records question reply/reject history back onto matching cards.
