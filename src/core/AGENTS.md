# src/core/ — Shared Contracts, Stores, Locks

## OVERVIEW

Shared data layer for every runtime. Defines card/scheduler/settings/script/Telegram/capability types, primary-agent and runtime-model defaults, cron parsing, retry helpers, secret detection, and filesystem-backed stores with dual locking — including the Scope Manager stores for Claude Code settings, MCP config, cold storage, and placement targets.

| Change card, screenshot, stale, feedback fields | `types.ts` | Shared by backend, web, tests |
| Change scheduler action/history schema | `types.ts`, `scheduler-store.ts` | Scheduler JSON lives in `schedulers.json` |
| Change settings secrets/toggles storage | `settings-store.ts` | Persists `settings.json` |
| Change synced script storage/history | `script-store.ts` | Persists `scripts.json`, syncs `KANBAN_DATA_DIR/scripts/` |
| Change settings/parameter env injection or redaction | `execution-environment.ts` | Shared by scheduler and ScriptExecutionService; `AK_PARAM_*` is reserved for validated parameters |
| Change Quick Action schema, validation, templates, or persistence | `types.ts`, `quick-action-store.ts` | `quick-actions.json`; Prompt run idempotency state is stored on the generated card |
| Change session lineage (what "이어진 세션" means) | `session-chain.ts` | `buildSessionChainMap(cards)` — pure, **symmetric** map of sessions that continue one another, from `parentCardId` / `queuedAfterCardId` / `resumeSessionId`. Self-links are dropped, so a queue step that stayed on one `sessionId` is not a relation. Must be fed archived cards too (`includeArchived: true` in `computeSessionAggregates`): the sessions this feeds — the Works Inbox — are usually already off the board |
| Change Work schema, session-linking (1:N), or Inbox ignore persistence | `types.ts`, `work-store.ts` | `works.json` (`{ works, ignoredSessionIds }`); a session links to at most one Work; sessions join by `sessionId`, card model untouched |
| Change the Inbox ignore list | `work-store.ts` | `ignoreSession` (append, idempotent) / `unignoreSession` (remove, **throws `WorkSessionNotIgnoredError` for an id that was never ignored**) / `getIgnoredSessionIds`. The list was append-only with no read route, which made `폐기` the one action in this domain with no way back — a mistyped `x` in the assign modal lost a session until someone hand-edited `works.json`. Restoring is deliberately not idempotent so a stale UI list cannot report success for a row already off it |
| Change Work lifecycle stamps (`resolvedAt`/`resolution`/`startedAt`) | `work-store.ts` | Terminal transitions auto-stamp `resolvedAt` + `resolution` (`done`→`completed`, `discarded`→`abandoned`, and a merge source→`superseded` + `supersededByWorkId` — `superseded` was once removed for being unreachable and came back **with** `mergeWork`, the transition that stamps it; the route still refuses it and `supersededByWorkId` on PATCH, since the pair is only meaningful together); returning to `active` clears all three; `startedAt` is `min()` over every linked session's earliest card time, so **any** link/unlink can move it. The store never reads cards: the caller injects a `WorkStartedAtResolver` and **the store runs it inside its own lock**, against the link set the write just produced — taking a pre-computed date instead was a TOCTOU that let two concurrent links overwrite each other's `min()`. The result is clamped to `resolvedAt` (via `Date.parse`, not string comparison) so a link edit cannot invert the bar. Card-level side effects live in `plugin/works/work-lifecycle.ts` — see `docs/invariants.md` |
| Mark or drop a link whose session lost every card | `work-store.ts` | `applyLinkCardPresence(workId, { missing, present })` stamps/clears `WorkSessionLink.cardsMissingAt` and reports only what changed (so an idempotent re-run writes nothing); `pruneMissingSessions(workId, resolver?)` removes the stamped links. The verdict is the caller's (`plugin/works/work-links.ts`) — the store still never reads cards. Pruning **keeps a Work it empties**: unlike `moveSession`, a cleanup has no destination, so taking the record, its Summary and its Timeline history as a side effect would be a bigger action than the button |
| Merge one Work into another | `work-store.ts` | `mergeWork(fromId, intoId, resolver?)` — one dual-lock transaction: move the links the target does not already hold (`linkedAt` and `role` preserved; a duplicate session is **skipped**, so the surviving record's own link is never silently rewritten), recalculate the target's `startedAt` with the injected resolver, and close the source as `discarded` + `superseded` + `supersededByWorkId`. Both ends go through the same `assertMovable` gate as `moveSession`. **The source is kept, not deleted** — unlike emptying a Work by moving its last session out, which deletes it and takes its Summary, notes and Timeline history with it. A self-merge throws `WorkMergeTargetError` before the lock |
| Filter/sort a Work list | `work-list.ts` | `selectWorks(works, query)` — the **one** rule behind `GET /api/works` *and* the web Active list (the client polls the whole list because the Timeline and the assign recommendations need every Work, so it narrows locally with this same function). Every comparator ends on `id` so the order is total; unparseable dates sink instead of throwing it off. `workPlanOverrunDays(work, now?)` is `active`-only — a resolved Work's `resolvedAt` is an end, not a missed forecast — and clamps to 1 day, because a manually set end lands at end-of-day and would floor to 0 for its first hours |
| Move a session link between Works | `work-store.ts` | `moveSession()` — one dual-lock transaction: re-parent the link, recalculate both sides' `startedAt` (injected `WorkStartedAtResolver`), delete a source left with zero links (a merge → response `from: null`). `assertMovable` requires both ends to be un-archived **and not `done`**: a `done` Work with no `archivedAt` is mid-completion (its sweep is only deferred), and it used to pass a gate that looked at `archivedAt` alone. `active ↔ active` and `discarded → active` are allowed. The `POST /api/works/:id/sessions` re-link `409` stays — moving is a separate verb, not a loosening of the 1:N invariant |
| Claim the Work completion sweep | `work-store.ts` | `claimArchiveSweep(id, updates)` — applies the `done` transition **and** stamps `archivedAt` in one locked write, returning `null` when it was already stamped. The idempotence guard has to be atomic: as a `getWork` read plus an `updateWork` write in separate lock sections, two concurrent `done` patches both saw "no `archivedAt`" and both swept. It shares `writeUpdate()` with `updateWork` so the terminal-stamp and date-order rules cannot drift. Because the stamp now precedes the card sweep, `applyWorkPatch` rolls it back when the sweep archives nothing |
| Map a Works failure to an HTTP status | `work-errors.ts` | One class per distinguished failure (`WorkNotFoundError`, `WorkSessionNotLinkedError`, `WorkSessionAlreadyLinkedError`, `WorkNotActiveError`, `WorkSessionNotIgnoredError`, `WorkNotMovableError`, `WorkDateOrderError`, `WorkCardsRunningError`, `WorkAlreadyActiveError` → 409, `WorkMergeTargetError` → 400). Routes classify on `instanceof`, **never** on the message — `message.includes('not found')` turned a card vanishing mid-sweep (`Card not found: <id>`) into `404 Work not found`. Add a class rather than a new substring |
| Change Work date validation | `work-store.ts` | `writeUpdate` (shared by `updateWork` and `claimArchiveSweep`) rejects an edit that leaves `resolvedAt < startedAt` with `WorkDateOrderError`, but **only when the caller passed a date** — so a record already stored inverted can still be edited back into shape. The Timeline's bar-edge drag and the detail dialog's date inputs both land here |
| Change the terminal `resolvedAt` auto-stamp | `work-store.ts` | It only fills in `now` when `resolvedAt` is *empty*, which is what lets an `active` Work carry a user-set **planned end** that survives the later completion. Do not make `done` overwrite an existing `resolvedAt` |
| Change subagent inheritance (which sessions a Work adopts) | `session-chain.ts` | `buildSubagentSessionTree(cards)` + `subagentAncestorSessions` / `subagentDescendantSessions` — the **directed** subset of the lineage map, following `parentCardId` only. Queue chains and `resumeSessionId` are excluded on purpose: a queued follow-up is a decision the user still gets to make, whereas a subagent session exists only because the parent spawned it. That asymmetry is what lets `POST /api/works/:id/sessions` carry a session's descendants into the same Work and lets the Inbox hide a subagent whose parent is already assigned. A child with two candidate parents takes the lexicographically smallest, so the tree does not depend on card order; both walks are cycle-safe. Archived cards required, same as `buildSessionChainMap` |
| Change what the Timeline draws (executed work, day buckets) | `timeline-aggregate.ts` | Pure: `cardExecutionSpan` (a card enters the grid only from `startedAt`/`completedAt`, never `createdAt` — a card parked in `todo` for months must stay invisible), `buildTimelineSessions` (rolls cards up into **session** rows, the grid's minimum unit; a session with no `sessionId` has no row to draw on, subagents are opt-in, overlap not containment decides inclusion), and `timelineArchiveMonths` (which archive months a window has to read), and `TimelineAggregateOptions.ignoredSessionIds` (a Works-discarded session keeps its row — it really ran — but comes back `ignored: true` so the row drops its 배정 button), plus `checkTimelineWindow` (the route's whole `400` vocabulary, including the `TIMELINE_MAX_WINDOW_DAYS` = 400 cap: the window is the *only* bound on how much archive gets parsed and it is an unauthenticated GET, so `from=1970&to=2030` used to read the entire archive) and `TimelineSessionSpan.truncatedBefore` (a session with cards that finished before `from` reports a `startedAt` that is **not** its real start, because those cards are outside the requested window — the flag is what lets the grid draw a cut left edge instead of claiming the session began on this grid). That last one is a correctness rule, not an optimization: archive files are keyed by `updatedAt` (UTC) and a card is never updated before it ran, so every month from the window's month **−1** upward is both necessary and sufficient. Compose `listArchiveMonths()`/`loadArchiveMonth()` here — never `loadArchives()`, whose full scan the wiki and Telegram paths depend on |
| Change what the Work detail dialog reads (archive-inclusive session summaries) | `timeline-aggregate.ts` | Also pure, and deliberately in the *same* module as the Timeline helpers because it has the same problem: completing a Work archives every card under it, so anything derived from the board list describes a finished Work as empty. `buildWorkSessionsResponse(work, cards, { archivedCardIds, scannedMonths })` rolls the links up into per-session titles/counts/wiki docs plus the whole-Work totals; `workCardScanFloor(work)` = `min(startedAt, createdAt, ...linkedAt)` is the window start to hand `timelineArchiveMonths`. A card carries no archived flag (`archivedAt` lives on the monthly file), so the caller reads board and archive separately and passes the archived ids — a card seen in both is counted once. Same hard rule as the Timeline: never `loadArchives()` |
| Lift archived cards back onto the board | `store.ts` | `unarchiveCards(cardIds, { months })` — the inverse of `archiveCards`, and the only writer of that direction. Mirrors the archive's `parentCardId` **subtree cascade** (a child left in the archive under a board parent is a split the board cannot render), skips ids already on the board, and rewrites each touched month file atomically. Two rules it must keep: card `status` is **not** touched (the completion sweep flipped everything to `done` and recorded the previous statuses nowhere, so cards come back `done`), and a `pending` `card.wiki` stamp is **cleared** while a decided one (`kept`/`skipped`/`failed`) is kept — the pending stamp is an unhonourable claim once the card is off the archive, and leaving it would block re-queueing since `archiveCards` only stamps when `!card.wiki`. `months` bounds which files get parsed; still never `loadArchives()` |
| Read a single card that may already be archived | `store.ts` | `getCard(id, { includeArchived })` falls back to the monthly archive files, newest month first, stopping at the first hit. This is what makes a *finished* card addressable — every deep link into completed work (a Timeline day cell, the Works Inbox "대화 보기") answered `404` without it. Still not `loadArchives()` |

## CONVENTIONS

- `types.ts` is the single source of truth for shared DTOs.
- Store classes resolve `~`, generate IDs with `nanoid()`, write temp files, then `renameSync()` atomically.
- Writes always go through in-process mutex + `FileLock`.
- Board, schedulers, settings, scripts, Telegram state, and placement targets each persist to separate JSON files.
- `description` is required on cards.
- `findCardBySessionId()` returns the newest matching card.
- `UpdateTelegramChatStateInput` uses `null` to clear persisted optional fields.
- Script and scheduler stdout/stderr are capped to 8KB by UTF-8 bytes.
- Execution settings env cannot replace interpreter/system/internal reserved keys. Script Quick Action parameters use only normalized `AK_PARAM_<UPPER_SNAKE_KEY>` names; masked settings and secret parameters must be redacted before persistence.
- `ScriptStore.beginRun()` is the atomic per-script concurrency claim. Terminal updates replace the matching running row, running entries cannot be deleted, and stale running rows are reconciled after process restart.
- Scheduled-dispatch reservations are store-owned and atomic: `scheduled -> dispatching -> dispatched/failed`, with explicit stale-claim recovery after restart.
- Quick Action card reservation is store-owned and atomic on `(quickActionId, quickActionRequestId)`; only the caller receiving `created: true` may dispatch it.
- Quick Action icon palette, duplicate policy, validation messages, and grapheme normalization live in `types.ts`. Omitted icons are claimed under the QuickActionStore dual lock; icon-less legacy entries receive deterministic, distinct fallbacks in display sort order.
- Primary-agent defaults live here; UI and plugin must not fork model/label maps.
- Clearing selected Telegram session/card state must not implicitly clear sticky default agent/model fields.
- `feedbackForCardId`, `telegramChatId`, and Telegram selected-session fields are part of fragile workflow contracts tracked in `docs/invariants.md`.
- `card.wiki` is written only by `archiveCards()` (pending stamp) and the wiki archive methods (`updateArchivedCardsWiki`, `markWikiPending`) — never through `updateCard()`. Wiki updates must not bump `card.updatedAt` (archive files are grouped by it).
- `resolveDir()` (leading-`~` expansion) lives in `data-dir.ts`; stores import it instead of redefining it.
- Writes to `~/.claude.json` always go through `safeMutateClaudeJson()` in `mcp-config-store.ts` — never a raw `readFileSync`/`writeFileSync` pair — because Claude Code itself writes that file concurrently and ignores our `FileLock`.
- Any MCP definition written into a `project` (team-shared) scope must pass through `detectPlaintextSecret()` first; callers surface `{ secretWarning: true }` instead of silently persisting a secret.
- `CapScope` (`'user' | 'project' | 'local' | 'cold'`) is the shared vocabulary for where a skill/MCP server lives; don't invent parallel scope strings.
- Cold storage entries are keyed by `kind:ref` (`skill:<runtime>/<name>` or `mcp:<name>`) inside `manifest.json`; MCP defs additionally live in their own `registry.json` since the original `~/.claude.json` entry is deleted on freeze.
- `placement-targets-store.ts` seeds three non-deletable builtins (`builtin-user`, `builtin-codex-user`, `builtin-cold`); `removeTarget()` must reject `builtin: true` targets.
- Missing persisted placement-target `runtime` migrates to `claude`; target dedupe uses `runtime + dir`.
- MCP inventory identity is `${runtime}:${name}`. Same-name Claude/Codex servers must never merge; same-runtime placements may merge.
- Claude MCP JSON/parser/writer/CLI fallback stays in `mcp-config-store.ts`. Codex support remains additive through `mcp-runtime-adapter.ts`.
- Codex TOML writes may replace only the selected `[mcp_servers.*]` table family; non-MCP tables/comments/order stay untouched.
- MCP write previews are read-only; apply routes explicitly call the existing Claude writer or the Codex writer. `alwaysLoad` is a Claude-only adapter capability.
- Cold MCP entries preserve their runtime and exact source placement; missing legacy metadata defaults to Claude/sourceScope.
- Codex inventory evaluates each registered directory from its git/project root down to the target directory; nearer `.codex/config.toml` definitions win for that target. Project trust is reported as required with status unknown, never inferred.
- MCP discovery is fail-open across runtimes and config layers: malformed Codex TOML becomes diagnostics and must not hide Claude MCP or persisted Skill inventory.

## ANTI-PATTERNS

- Duplicating shared interfaces in `web/`, `plugin/`, or tests
- Writing JSON directly outside store classes
- Adding a new persisted store without temp-file + dual-lock behavior
- Hardcoding agent labels/models outside `agent-config.ts`
- Hardcoding a per-runtime model list outside `runtime-config.ts`
- Mutating `~/.claude.json` without going through the CAS engine in `mcp-config-store.ts`
- Re-serializing all of Codex `config.toml` to modify one MCP server
- Skipping `detectPlaintextSecret()` before writing an MCP def into project/team-shared scope

## NOTES

- `store.ts` also owns screenshot persistence, queue ordering helpers, and scheduled-dispatch recovery helpers.
- `script-store.ts` tags runtime-synced entries with `Synced from data scripts/<file>` descriptions.
- `settings-store.ts` carries runtime toggles such as `network_exposed` and secret tokens.
- `retry.ts` is the shared utility for retryable runtime edges.
- `mcp-config-store.ts` prefers shelling out to the `claude` CLI (`claude mcp add/remove`) when available and operating on the real `~/.claude.json`, falling back to the CAS engine otherwise (always used for overridden paths in tests).
- `cold-storage-store.ts` rejects symlinks on all move/copy/freeze/restore operations (`guardNotSymlink`) and verifies directory hashes after cross-volume copies before deleting the source.
