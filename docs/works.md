# Works & Timeline

## 개요

**Work**는 여러 에이전트 세션을 하나로 묶는 *사람 의도 단위*의 작업 엔티티입니다.

카드(`KanbanCard`)는 "한 번의 실행"이고 세션은 "한 번의 대화"지만, 사람이 실제로 인식하는 작업 단위는 그보다 큽니다. 예를 들어 "Works 탭 만들기"라는 하나의 일이 `개발 세션 → 리뷰 세션 → 버그 수정 세션` 3개로 나뉘어도, 사람에게는 여전히 하나의 작업입니다. Work는 그 묶음을 1급 객체로 만듭니다.

- **세션 : Work = N : 1** — 한 세션은 최대 하나의 Work에만 소속됩니다. 서버가 재연결(re-link)을 거부합니다.
- **Work는 절대 자동 생성되지 않습니다.** 새 세션은 Works 탭의 **Inbox**에 쌓이고, 사용자가 배정하거나 폐기할 때까지 남아 있습니다.
- **카드 모델은 건드리지 않습니다.** Work는 `sessionId`로만 조인하며, 저장소도 별도입니다(`~/.agent-kanban/works.json`).

관련 타입은 모두 `src/core/types.ts`의 `Work` / `WorkSessionLink` / `WorkInboxSession` / `WorksConfig` 입니다.

### 상태 전이

| 상태 | 의미 | 카드에 대한 부수효과 |
|------|------|----------------------|
| `active` | 진행 중. `resolvedAt`이 없습니다 → Timeline 바가 오늘까지 연장됩니다 | 없음 |
| `done` | 완료. `resolvedAt` 자동 기록 | 산하 모든 카드를 `done`으로 바꾸고 **일괄 archive** (→ wiki 파이프라인으로 넘어감). **즐겨찾기 카드는 제외** — 아래 [즐겨찾기 카드는 sweep에서 빠진다](#즐겨찾기-카드는-sweep에서-빠진다) |
| `discarded` | 폐기. `resolvedAt` 자동 기록 | 없음. 카드는 보드에 남고, `WikiWorker`는 이 Work의 그룹핑만 해제합니다(세션 단위로 일반 처리) |

터미널 상태는 **일방통행이 아닙니다.** `POST /api/works/:id/reopen`이 `done` / `discarded` → `active`로 되돌리고 일괄 archive된 카드를 보드로 복원합니다 — 아래 [재개](#재개-post-apiworksidreopen).

`resolution`은 `completed` / `abandoned` / `superseded` 셋 중 하나로, 터미널 상태 전이 시 자동으로 채워집니다(`done` → `completed`, `discarded` → `abandoned`, [병합](#work-병합-post-apiworksidmerge)의 원본 → `superseded`).

> **`superseded`는 한 번 제거됐다가 되돌아온 값입니다.** 예전에는 이 값을 쓰는 코드가 한 곳도 없어서 — 병합처럼 보이는 유일한 경로(마지막 세션을 옮겨 원본을 비우는 이동)는 원본 Work를 *삭제*하므로 스탬프할 대상이 없었습니다 — 타입과 라우트 검증에서 함께 뺐고, 규칙은 "되살릴 때는 **그것을 찍는 전이와 같이** 추가하라"였습니다. `POST /api/works/:id/merge`가 그 전이입니다.
>
> **단, PATCH로는 여전히 쓸 수 없습니다**(`400 Invalid resolution`). `superseded`는 "세션이 어디로 갔는지"를 담는 `supersededByWorkId`와 짝일 때만 의미가 있고, 그 둘을 함께 쓰는 것은 merge 라우트뿐입니다 — 클라이언트가 한쪽만 써 넣으면 아무 곳도 가리키지 않는 `병합됨` Work가 됩니다. `supersededByWorkId`도 같은 이유로 patch 거부 필드입니다.

> 완료의 일괄 archive는 되돌릴 수 없는 동작입니다. `works.done_confirm`은 **기본값이 `true`** 이고, 켜져 있으면 완료는 전용 확인 다이얼로그를 반드시 거칩니다 — [완료 / 폐기 확인 다이얼로그](#완료--폐기-확인-다이얼로그) 참고.
>
> **실행 중인 에이전트가 있는 카드를 가진 Work는 완료할 수 없습니다** (`409`). 실행 중 카드를 archive하면 그 카드의 완료 훅이 `Card not found`로 실패하고 wiki가 미완성 트랜스크립트로 문서를 만듭니다.

#### 즐겨찾기 카드는 sweep에서 빠진다

`favorite`은 "이 카드를 보드에 고정한다"는 뜻이고, `store.archiveCards()`는 cascade로 딸려가는 **자식** 카드에 대해 이미 그것을 지킵니다. Work 완료만이 자기 최상위 seed를 직접 넘겨서 그 표시를 지나쳤습니다 — 별을 붙여둔 카드가 확인도 되돌리기도 없이 보드에서 사라졌습니다.

- 즐겨찾기 최상위 카드는 **archive하지도, `done`으로 바꾸지도 않습니다.** `done`으로만 바꾸면 다음 일반 archive(`POST /api/archive`, id 없이 = 보드의 모든 `done`)에 쓸려가므로 고정이 고정이 아니게 됩니다.
- 응답의 `sweep.keptFavoriteCardIds`로 보고하고, 완료 확인 다이얼로그가 `⭐ 즐겨찾기 카드 N장은 보드에 그대로 남습니다`로 미리 알립니다(`describeKeptFavorites`, 순수 함수).
- `GET /api/works/:id/completion-preview`의 `sweepCardCount`도 즐겨찾기를 빼고 셉니다. 다이얼로그가 약속하는 숫자와 sweep이 실제로 하는 일은 같아야 합니다.
- 즐겨찾기 카드의 실행 중 run은 완료를 막지 **않습니다**. sweep이 그 카드를 가져가지 않으므로 막을 이유가 없습니다.
- 보드에 남은 카드가 **전부** 즐겨찾기면 `archiveSkipped: 'favorites-only'`이고 `archivedAt`을 찍지 않습니다 — 별을 떼고 다시 완료할 수 있어야 하기 때문입니다.
- 필터는 `applyWorkPatch`에 있습니다(`store.archiveCards`가 아니라). `POST /api/archive`의 동작을 바꾸지 않기 위한 것이니 store 쪽으로 옮기지 마세요.

#### 한 Work = 한 문서 (`Work.wikiDocPath`)

`WikiWorker`의 그룹핑 인덱스에는 `active` Work도 들어갑니다 — 완료 전에 손으로 archive한 카드도 그 Work의 문서에 속하기 때문입니다. 그래서 **한 Work의 카드가 여러 배치로 큐에 들어오는 것이 정상**입니다(먼저 archive된 카드 한 장, 나중에 완료 sweep이 나머지).

예전에는 재작성 대상 경로를 **그 배치 안의 카드**에서만 찾았습니다. 두 번째 배치의 카드는 자기가 참여하지 않은 배치의 `docPath`를 갖고 있지 않으므로, 같은 Work 제목으로 `troubleshooting/x.md`와 `troubleshooting/x-2.md` 두 문서가 생겼습니다.

지금은 문서를 쓴 뒤 그 경로를 **Work 레코드에 기록**하고(`Work.wikiDocPath`, best-effort), 다음 배치가 그것을 `overwritePath`로 씁니다. 카드 쪽 `wiki.docPath` 폴백은 세션 단위 그룹과 과거 데이터를 위해 그대로 남아 있습니다.

### 날짜 규칙 — `startedAt`은 항상 `min()`

```
Work.startedAt = min(연결된 모든 세션의 최초 카드 시각)
```

- **연결 / 해제 / 이동 세 경로 모두**에서 재계산합니다. "첫 연결에서만 back-date하고 이후 링크는 시작을 움직이지 않는다"는 예전 규칙(`isFirstLink` 특례)은 폐기됐습니다 — 9/3에 만든 Work에 9/1에 시작한 세션을 붙이면 바가 9/1로 당겨집니다.
- 세션의 최초 시각은 그 세션 카드들의 `startedAt`(없으면 `createdAt`) 중 가장 이른 값이며, **archive된 카드까지 포함**해 계산합니다(triage 시점엔 이미 끝난 세션이 흔합니다).
- 카드가 하나도 없는 세션은 그 링크의 `linkedAt`으로 폴백하고, 링크가 아예 없는 Work는 현재 값을 유지합니다.
- 세션이 빠져서 `min()`이 늦어지는 것도 정상입니다(남은 세션 중 가장 이른 날짜).
- `resolvedAt`은 완료/폐기 시각이지 세션에서 파생되는 값이 아니므로 건드리지 않습니다. 단 재계산 결과가 `resolvedAt`보다 늦어지면 바가 역전되지 않도록 `resolvedAt`으로 clamp합니다(폭 0인 바).

- **링크가 바뀌면 손으로 찍은 `startedAt`도 재계산 값으로 덮입니다.** 연결·해제·이동·정리 뒤의 시작일은 언제나 파생값입니다. 바 드래그로 맞춰둔 날짜를 지키고 싶다면 링크를 건드린 뒤 다시 찍어야 합니다. 단 **아무 링크도 바꾸지 않은 요청은 재계산하지 않습니다** — 그 Work가 갖고 있지 않은 세션에 대한 `DELETE`는 no-op이고 `updatedAt`조차 건드리지 않습니다.

구현은 `src/plugin/works/work-lifecycle.ts`의 순수 함수 `resolveWorkStartedAt(cards, work)`와, 그것을 감싸는 단일 진입점 `createWorkStartedAtResolver(cards)` 하나입니다. 이동 다이얼로그의 영향 미리보기도 같은 순수 함수를 씁니다 — **날짜 계산을 다른 곳에 다시 구현하지 마세요.**

**재계산은 store의 락 안에서 일어납니다.** 라우트는 archive를 포함한 카드 스냅샷을 **요청당 한 번** 읽어 resolver로 감싸 넘기고, `WorkStore.addSession` / `removeSession` / `moveSession` / `pruneMissingSessions`가 각자 방금 쓴 링크 집합에 대고 그것을 실행합니다. 두 가지가 이 설계의 이유입니다.

| 예전 | 결과 |
|------|------|
| 라우트가 락 **밖에서** `min()`을 계산해 값으로 넘김 | 동시 연결 두 건이 각각 "상대 세션이 없는 링크 집합"의 `min()`을 계산했고, 나중에 쓴 쪽이 상대의 답을 덮어써 `min()` 불변식이 깨졌습니다 |
| 링크마다 `getCards({ includeArchived: true })`(아카이브 전체 스캔) 재호출 | 세션 20개 배정 = 20회 이상의 전체 스캔. 지금은 요청당 1회이고, 배치 연결도 그 하나를 공유합니다 |

## 화면

### ① Works 탭

세 섹션이 위에서 아래로 쌓입니다.

- **📥 Inbox — 미배정 세션**: 아직 Work에 속하지 않고 폐기되지도 않은 세션 중 **정리 대상인 것만** ([Inbox에 무엇이 들어오는가](#inbox에-무엇이-들어오는가) 참고). `배정` 버튼을 누르면 행 아래로 인라인 패널이 펼쳐지고, `새 Work 만들기`(제목은 첫 프롬프트에서 자동 제안) 또는 `기존 Work에 연결`(같은 `projectDir`의 active Work를 우선 추천) 중 하나를 고릅니다. 세션 역할(`개발`/`리뷰`/`디버그`)도 함께 지정합니다. 여러 세션을 한 Work로 묶으려면 아래 [다중 선택 배정](#다중-선택-배정-드래그--체크박스)을 씁니다.
- **🔵 Active Works**: 진행 중인 Work 목록. 검색·디렉토리 필터·정렬을 갖습니다([Active 목록의 검색 · 필터 · 정렬](#active-목록의-검색--필터--정렬)). `works.stale_days`(기본 5일)를 넘긴 Work에는 `⚠ N일째 미완료` 배지가, 예정일이 지난 Work에는 `예정 N일 초과` 칩이 붙습니다. 행의 `완료…`는 **ghost 버튼**이고 확인 다이얼로그만 엽니다 — 예전에는 초록 primary(`kv2-btn--success`)여서, `상세`를 누르려고 접근하는 행에서 가장 눈에 띄는 표적이 곧 되돌릴 수 없는 일괄 archive였습니다.
- **✅ Resolved**: 완료/폐기된 Work **전체**. 기본은 접힌 상태이고 헤더에 `전체 N개`만 보여줍니다. `펼치기 ▼`를 누르면 종료 최근 순으로 전부 나옵니다 — **날짜 창(예전의 "최근 7일")은 없습니다.** 오래된 Resolved야말로 일부러 찾아 여는 대상이고, 평소엔 화면에서 빠져 있어야 Active/Inbox가 가려지지 않기 때문입니다. `resolvedAt`이 없는 레코드는 `updatedAt`으로 정렬됩니다(순수 함수 `resolvedWorksNewestFirst`).

#### Active 목록의 검색 · 필터 · 정렬

Active 목록은 `updatedAt` 내림차순 **고정**이었습니다. 그것은 이 목록이 실제로 받는 질문에 대한 잘못된 순서입니다 — 3주째 아무도 안 건드린 Work가 맨 아래, 즉 이미 안 보이던 자리로 가라앉습니다. 그리고 여러 리포지토리에 Work가 열두 개쯤 있으면 이름으로 하나를 찾을 방법이 없었습니다.

섹션 헤딩과 목록 사이에 컨트롤 세 개가 있습니다(Inbox와 Resolved는 영향받지 않습니다).

| 컨트롤 | 동작 |
|--------|------|
| 검색 | 제목 · `projectDir` · **메모** · Summary 줄을 대소문자 무시로 부분 일치. Work가 "무엇에 관한 것인가"를 말하는 두 필드가 메모와 Summary이므로, 제목만 뒤지면 배정 당시의 첫 프롬프트로만 찾을 수 있습니다 |
| 디렉토리 | 정확 일치. active Work의 디렉토리가 2개 이상일 때만 나타납니다(`workProjectDirs`) |
| 정렬 | `최근 활동`(기본) / `오래 방치된 순` / `예정일 임박순` (`WORK_LIST_SORT_LABELS`) |

- 규칙은 **순수 함수 `selectWorks(works, query)` 하나**입니다(`src/core/work-list.ts`). `GET /api/works`가 적용하는 것과 **같은 함수**이므로 서버 응답과 클라이언트 화면이 갈라지지 않습니다.
- 그런데도 **좁히기는 클라이언트에서** 합니다. Works 폴링은 목록 *전체*를 가져와야 하고(Timeline 그룹핑·배정 추천·이동 다이얼로그가 모든 Work를 봅니다), 요청을 좁히면 그 셋이 깨집니다.
- `오래 방치된 순`은 `최근 활동`의 정확한 거울입니다. `예정일 임박순`은 `resolvedAt` 오름차순이고 **예정일 없는 Work를 전부 뒤로** 보냅니다(그 안에서는 최근 활동순) — 예정일 없음을 "가장 급함"으로 정렬하면 목록이 뒤집힙니다.
- 모든 비교자는 `id` 비교로 끝나므로 **전순서**입니다. `updatedAt`이 밀리초까지 같은 두 Work가 폴링마다 자리를 바꾸지 않습니다.
- 헤딩은 좁혀졌을 때 `2 / 3개`로 그 사실을 보고하고, 결과가 없으면 "진행 중인 Work가 없습니다"가 아니라 `검색·필터 조건에 맞는 Work가 없습니다`라고 말합니다. 빈 탭과 빈 검색 결과는 다른 상황입니다.

##### 예정일 초과 (`예정 N일 초과`)

`active` Work의 예정일이 지났는지는 화면에 **전혀 표시되지 않았습니다.** 목록은 `시작 8/26`만 말하고, Timeline은 과거의 어떤 날에서 멈춘 바를 아무 표시 없이 그렸습니다 — 다음 주에 끝나는 바와 3주 전에 끝났어야 하는 바가 똑같이 생겼습니다.

- 일수는 순수 함수 `workPlanOverrunDays(work, now?)`(`src/core/work-list.ts`) 하나에서 나오고, 목록 칩·상세 `기간` 행·Timeline 바가 모두 그것을 씁니다.
- **`active`만** 대상입니다. 종료된 Work의 `resolvedAt`은 실제 종료 시각이지 놓친 예측이 아니므로, 그것을 초과로 세면 Resolved 목록 전체에 경고가 붙습니다.
- 방금 지난 예정일은 `0일 초과`가 아니라 **최소 1일**로 보고합니다(손으로 찍은 예정일은 그날 end-of-day에 놓이므로 floor하면 첫 몇 시간이 0이 됩니다).
- 표현은 `--kv2-warn-*` 계열입니다 — danger가 아닙니다. 고장난 것이 아니라 계획이 작업보다 오래된 것입니다. 목록 카드는 왼쪽 accent 스트라이프까지 warn으로 바뀌어 **스크롤만으로 찾을 수 있습니다**(`.works-card--overrun`), Timeline 바는 채움색이 바뀌고 `▸ M/D 예정`이 `▸ 예정 N일 초과`로 바뀝니다(`.tl-bar--overrun`).
- `⚠ N일째 미완료`(`works.stale_days`, "N일 동안 아무 일도 없었다")와는 **다른 불만**이고 동시에 참일 수 있으므로, 하나로 합치지 않고 각각의 표시를 유지합니다.

#### Inbox에 무엇이 들어오는가

Inbox는 **보관소가 아니라 정리 대기열**입니다. 예전에는 "미배정이고 폐기되지 않은 세션 전부"였는데, 피어 런타임이 열려 있는 세션을 전부 보고하므로 카드가 하나도 없는 `(No linked card)` 행이 기간·개수 제한 없이 쌓이고 Works 탭 배지가 영구히 켜져 있었습니다. 지금은 서버(`GET /api/works/inbox`)가 네 가지를 걸러냅니다.

| 제외되는 것 | 이유 |
|-------------|------|
| Work에 이미 연결된 세션 / 폐기(`ignoredSessionIds`)한 세션 | 예전과 같음. 폐기한 세션은 [무시한 세션 목록](#무시한-세션-목록-폐기의-복구-경로)에서 되돌릴 수 있습니다 |
| **카드가 하나도 없는 세션** | 실행 기록이 없으므로 배정할 작업이 없습니다. 런타임이 세션만 열어둔 상태 |
| **부모가 이미 배정된 subagent 세션** | 부모의 Work가 이미 소유합니다 — 아래 [subagent 승계](#subagent-승계-부모의-work를-그대로-따라간다) |
| `since` 창(**기본 30일**)을 벗어난 세션, `limit`(**기본 200**) 초과분 | 두 달 전에 끝나고 아무도 배정하지 않은 세션은 정리 대상이 아니라 잔여물입니다 |

- **실행 중인 세션은 창과 무관하게 남습니다**(`cardStatus === 'in_progress'`). 지금 돌고 있는 에이전트는 시각이 무엇이든 정리 대상입니다.
- 두 창은 쿼리로 열 수 있습니다: `?since=all&limit=all`. 웹은 기본값을 그대로 쓰므로 탭 배지도 이 창 기준입니다.
- 정렬은 **최근 활동순**(`updatedAt` 내림차순)입니다. 헤더 문구도 `· 최근 활동순`입니다 — 예전 문구 `· 오래된 것부터`는 실제 정렬과 반대였습니다.

##### 행에서 바로 보이는 것: 상태 칩과 계보 마크

배정 판단은 "이 세션이 지금 어떤 상태인가"와 "무엇에서 이어졌는가" 두 가지로 갈리는데, 예전에는 둘 다 행에 없었습니다(계보는 `배정`을 눌러 패널을 연 뒤에만 보였습니다). 이제 행 메타 줄이 둘 다 싣습니다.

| 표시 | 조건 | 순수 함수 |
|------|------|-----------|
| `subagent` (보라 외곽선) | `sessionKind === 'subagent'` — 부모가 아직 미배정인 subagent 세션 | `describeSessionState()` |
| `실행 중` (진행중 노랑) | `cardStatus === 'in_progress'` | 〃 |
| `미실행` (회색) | `cardStatus === 'todo'` — 한 번도 dispatch되지 않음 | 〃 |
| 칩 없음 | `complete` / `done` — **끝난 세션이 기본**이므로 조용히 둡니다 | 〃 |
| `🔗 이어진 Work N` | 그 계보를 이미 가진 Work가 N개 (배정 근거) | `chainedWorkIds()` |
| `🔗 이어진 세션 N` | 계보는 있지만 아직 어떤 Work도 갖고 있지 않음 | `relatedSessionIds.length` |

`subagent`가 카드 상태보다 위입니다 — 그 행의 실제 문제는 자기 카드가 무엇을 하고 있느냐가 아니라 **바로 위/아래에 있는 부모 행과 중복**이라는 점입니다. `works.assign_suggest_resume_chain`을 끄면 🔗 마크도 함께 사라집니다(추천 재정렬과 같은 스위치).

#### subagent 승계 (부모의 Work를 그대로 따라간다)

subagent 세션은 독립된 작업이 아닙니다 — 부모 카드가 낳았기 때문에만 존재합니다. 그래서 **부모 세션이 Work에 연결되면 그 자손 세션도 같은 Work에 자동 연결**됩니다(`POST /api/works/:id/sessions`, transitive).

- 계보는 `parentCardId` **하나만** 따릅니다(`buildSubagentSessionTree`, `src/core/session-chain.ts`). 큐 체인(`queuedAfterCardId`)과 `resumeSessionId`는 **제외**입니다: 큐로 이어진 다음 작업은 사용자가 여전히 판단할 몫이지만, subagent는 판단할 것이 없습니다. `buildSessionChainMap`이 대칭 무방향 맵인 데 반해 이쪽은 **방향이 있는** 부분집합입니다.
- **이미 다른 Work에 연결된 세션은 건너뜁니다.** 1:N 불변식은 저장소의 것이고, 이 경로가 우회 수단이 되어서는 안 됩니다.
- 사용자가 고른 `role`/`projectDir`은 고른 그 세션에만 붙습니다. 승계된 세션은 기본값입니다.
- 링크는 세션 하나씩 store의 락 안에서 `min()`을 다시 계산합니다 — 배치라고 재계산을 한 번으로 줄이지 않습니다. 공유되는 것은 **카드 스냅샷**이지 계산이 아닙니다.
- 응답은 `Work` + `cascadedSessionIds`입니다(`WorkAddSessionResponse`).
- **승계 이전에 연결된 Work**에는 자손이 Inbox에 남아 있을 수 있습니다. `POST /api/works/reconcile-subagents`가 그 1회성 보정 경로이고 멱등입니다.

#### 다중 선택 배정 (드래그 → 체크박스)

"이 세션들 전부 같은 작업"인 경우가 triage의 대부분이라, Inbox는 배치 배정을 1급으로 지원합니다.

| 동작 | 결과 |
|------|------|
| 행 위를 **위/아래로 드래그** | 지나간 행이 전부 선택되고, 그 순간 모든 행에 체크박스가 나타납니다. **마우스/펜 전용입니다** — 아래 참고 |
| 선택 상태에서 **행 클릭** | 그 행만 토글 — 안 눌린 건 추가, 이미 눌린 건 해제 |
| 헤더 `☑ 선택` | 드래그 없이 선택 모드 진입 (키보드/체크박스만으로 쓰는 경로) |
| 리스트 아래 `배정하기 (N)` | 선택 전체를 **하나의 Work**로 배정하는 패널을 엽니다. 열릴 때 `scrollIntoView({ block: 'nearest' })`로 화면에 들어오고, 상단에 선택한 세션 칩이 나열됩니다(칩의 `×`로 개별 해제) |
| `선택 끝내기` / `선택 해제` | 선택을 비우고 체크박스를 걷습니다 — **세 버튼(헤더 토글 · 액션 바 · 배정 패널) 모두 같은 `clearSelection()`** 입니다. 예전에는 액션 바의 `선택 해제`만 선택 집합을 비우고 선택 모드에 남아 있었습니다 |

- **선택 모드에서는 행 액션(`배정` / `대화 보기` / `폐기`)이 숨습니다.** 행 자체가 토글이므로 그 위에 놓인 버튼 3개는 오조작 표적이면서 드래그 시작면을 가렸습니다. 선택 모드에 들어가면 열려 있던 단일 행 패널도 접힙니다.
- 선택 모드의 행은 `role="button"` + `tabIndex=0` + `aria-pressed`이고 **Enter/Space로 토글**됩니다(체크박스는 자기 Space를 그대로 유지).
- **터치에서는 드래그 선택이 동작하지 않습니다.** `WorksView`의 `pointerdown` 핸들러가 `event.pointerType === 'touch'`를 그대로 반환합니다 — 터치 드래그를 선택으로 삼키면 Inbox를 손가락으로 스크롤할 방법이 사라지기 때문입니다. 기능 손실은 아닙니다: 헤더 `☑ 선택`이 같은 선택 모드로 들어가는 동등 경로이고, 그 뒤로는 탭 한 번이 곧 토글입니다. 표의 첫 줄이 모든 입력 장치에 적용되는 것처럼 읽히던 것을 여기서 좁힙니다.
- 폴링이 선택된 세션을 전부 걷어가면 선택 집합만이 아니라 **배정 패널도 함께 닫힙니다**. 예전에는 `bulkPanelOpen`이 남아, 다음에 아무 행이나 체크하는 순간 요청하지 않은 패널이 저절로 펼쳐졌습니다.
- 부분 실패한 세션은 **그 행에 이유가 표시됩니다**(`⚠ 배정 실패 — <서버 메시지>`). 공용 배너는 첫 이유 + `외 N개`뿐이라 어느 행이 실패했는지 알 수 없었습니다.
- 드래그는 **가산적**입니다. 두 번째 sweep은 이전 선택을 교체하지 않고 더합니다 — 잘못 들어온 행은 클릭으로 빼면 됩니다.
- 배정 패널은 **`WorkAssignInline`을 그대로 재사용**합니다(단일 배정·세션 이동과 같은 컴포넌트). 선택 집합은 `mergeSessionsForAssign()`으로 **대표 세션 하나**로 접혀서 들어가므로 추천 랭킹·제목 제안이 단일 배정과 동일한 구현을 씁니다. 대표 세션은 가장 오래된 세션이고, `projectDir`은 **선택 전체가 같은 디렉토리일 때만** 살아남습니다(섞여 있으면 `undefined` → "같은 디렉토리" 추천도, 새 Work의 `projectDir`도 없음). `bulk` prop은 문구만 바꿉니다.
- 링크는 **한 번의 배치 요청**입니다(`POST /api/works/:id/sessions/batch`, `useWorks.assignSessionsToWork`). 예전의 "세션마다 순차 POST"는 요청마다 아카이브 전체를 스캔해서, 20개를 고른 클릭 한 번이 20회 이상의 전체 스캔이었습니다. 배치는 카드 스냅샷 하나를 모든 링크가 공유합니다.
- **부분 성공은 여전히 정상 결과**이고, 이제 그것이 서버 응답의 형태입니다(`{ work, linkedSessionIds, cascadedSessionIds, failed[] }`). 1:N 불변식은 세션 단위이므로 이미 다른 Work에 속한 세션 하나가 성공한 링크들을 되돌리지 않습니다. 실패한 세션만 Inbox에 남아 **그대로 선택된 채**로 재시도할 수 있고, 이유는 그 행과 공용 에러 배너 양쪽에 나옵니다.
- `createWorkFromSessions`는 생성 → 전체 링크 순서로 실행하고, **하나도 링크되지 않으면 만든 Work를 되돌려 삭제**합니다(세션 없는 Work는 Timeline에 빈 바로만 남기 때문 — `moveSessionToNewWork`와 같은 규칙).

##### 드래그 구현에서 건드리면 안 되는 것

간트 바 드래그와 같은 이유로 기하 계산은 순수 함수(`worksAssign.ts`의 `rowIndexAtPointer` / `sessionIdsBetween`)에 있고 컴포넌트는 측정·렌더만 합니다.

- **고무줄 사각형은 그리지 않습니다.** 선택이 행 단위로 snap되므로 밴드가 표시할 정보가 체크박스+행 하이라이트와 완전히 겹칩니다 — 드래그 중 표시는 그 둘이 전부입니다(드래그 플래그는 텍스트 선택만 막습니다).

- **행 단위 hit-test**입니다. 픽셀 사각형 교차가 아니라 "포인터 아래 행"을 찾고, 리스트 밖으로 끌면 양 끝으로 clamp합니다(`columnAtPointer`와 같은 관례). 드래그 중 목록이 리플로우돼도 어긋나지 않습니다.
- 앵커는 **인덱스가 아니라 `sessionId`** 로 잡습니다. 드래그 중에 Inbox 폴링(10초)이 순서를 바꿔도 시작점이 밀리지 않습니다.
- 행 좌표는 캐시하지 않고 **매 move마다 재측정**합니다.
- 선택 액션 바는 **리스트 아래**에 렌더합니다. 위에 두면 드래그가 시작되는 순간 바가 삽입돼 모든 행이 포인터 밑에서 내려갑니다.
- **pointer capture는 press가 아니라 임계값(4px)을 넘긴 첫 move에서** 잡습니다. press에서 잡으면 캡처가 click 같은 호환 마우스 이벤트까지 컨테이너로 돌려버려서 **행 클릭 토글이 죽습니다**(실제로 e2e가 이걸 잡았습니다). 캡처를 늦게 잡은 덕에 드래그 끝의 click도 함께 삼켜져서, sweep이 끝난 행을 다시 토글하지 않습니다.
- 종료는 `pointerup` / `pointercancel` / `lostpointercapture` **셋 다** 듣습니다. 임계값을 못 넘긴 press는 캡처를 안 했으므로 마지막 신호가 오지 않고, 이 핸들러는 커밋이 아니라 정리만 하므로(선택은 move마다 이미 반영됨) 두 번 불려도 안전합니다 — 바 끝 드래그가 `lostpointercapture` 하나만 듣는 것과는 사정이 다릅니다.

Inbox에 세션이 남아 있으면 상단 탭의 **Works** 라벨 옆에 미배정 개수 배지가 표시됩니다. 이 배지는 Works 탭이 비활성일 때도 갱신됩니다(Inbox만 10초 주기로 상시 폴링).

#### 무시한 세션 목록 (폐기의 복구 경로)

Inbox 헤더의 `🗑 무시한 세션 N개`를 누르면 폐기한 세션 목록이 헤더 아래로 펼쳐지고, 각 행의 `복원`이 세션을 Inbox로 되돌립니다.

`ignoredSessionIds`는 **추가만 가능한 목록이었고 읽는 라우트도 없었습니다.** 그래서 Inbox 행의 `폐기` 한 번, 또는 모달에서 잘못 누른 `x` 한 번이 세션을 Inbox·탭 배지·Timeline 배정 버튼에서 영구히 지웠고, 복구 수단은 `works.json` 수기 편집뿐이었습니다.

| 라우트 | 하는 일 |
|--------|---------|
| [`GET /api/works/ignored-sessions`](./api-reference.md#get-apiworksignored-sessions) | 목록 + 각 행의 Inbox 요약(`session`) + `returnsToInbox` |
| [`DELETE /api/works/ignore-session/:sessionId`](./api-reference.md#delete-apiworksignore-sessionsessionid) | 목록에서 제거. 목록에 없던 id는 `404` |

- 행은 **첫 프롬프트로 식별**합니다(요약이 없으면 짧은 세션 id). 카드가 하나도 남지 않은 id도 목록에 남습니다 — 여전히 무시 상태이고, 목록에서 빼는 방법은 복원뿐이기 때문입니다.
- `returnsToInbox`가 `false`면 행에 `⚠ 복원해도 Inbox에는 나타나지 않습니다`가 붙습니다. 서버가 **Inbox와 같은 술어**(`isInboxTriageMaterial`)로 계산합니다 — 카드가 없거나, 부모가 이미 배정된 subagent거나, `since` 창을 벗어난 세션입니다. 복원 자체는 막지 않고 사실만 알립니다.
- 목록은 **폴링하지 않습니다.** Works 탭이 활성화될 때, 그리고 폐기/복원 직후에만 다시 읽습니다.
- Inbox가 비어 있어도 무시한 세션이 있으면 **Inbox 섹션은 계속 렌더**됩니다. 이 목록에 들어가는 유일한 입구가 그 헤더이므로, 헤더를 숨기면 Inbox가 깨끗해진 순간 폐기한 세션이 복구 불가가 됩니다.

폐기는 **되돌리기 토스트**도 함께 띄웁니다 — 아래 [결과 토스트](#결과-토스트-worksessionnotice) 참고.

### ② 모두 배정하기 모달

Inbox 헤더의 `⚡ 모두 배정하기`는 미배정 세션을 카드 스택처럼 하나씩(`n / N` 카운터) 훑는 키보드 우선 모달입니다.

| 키 | 동작 |
|----|------|
| `N` | 새 Work 만들기로 전환 (제목 입력칸이 열리며 자동 제안값이 채워짐) |
| `1`–`9` | 추천 Work 중 n번째 선택 (같은 `projectDir` 우선, 그다음 최근 활동순) |
| `S` | 건너뛰기 — 이 세션은 Inbox에 그대로 남습니다 |
| `X` | 폐기 — 세션을 무시 목록에 넣습니다 (Work 없이 보관) |
| `Enter` | 현재 선택으로 연결하고 다음 세션으로 |

배정 mutation은 인라인 패널과 **완전히 동일한 함수**(`useWorks`의 `createWorkFromSession` / `linkSessionToWork` / `ignoreSession`)를 씁니다. 두 경로가 갈라지지 않게 하려면 항상 훅 쪽을 고쳐야 합니다.

##### 어떤 키가 언제 단축키인가 — `resolveBulkAssignShortcut` (순수)

핸들러는 `window` **capture** 단계에 붙으므로 다이얼로그 안의 **모든** 키가 포커스 위치와 무관하게 들어옵니다. 그래서 "이 키가 지금 단축키인가"는 순수 함수 하나(`worksAssign.ts`)이고 유닛 테스트가 지킵니다.

| 규칙 | 결과 |
|------|------|
| target이 `<button>` / `<a>` / `contenteditable`이면 `Enter`는 **그 요소의 것** | `×`, `X 폐기`, `S 건너뛰기`, `연결하고 다음`에 포커스한 Enter는 그 버튼을 누릅니다 |
| target이 `INPUT` / `TEXTAREA` / `SELECT` / `contenteditable`이면 **`Enter`만** 단축키 | 제목 입력의 Enter는 제출, 글자·숫자는 전부 그 컨트롤로 |
| `1`–`9`는 추천 개수를 넘으면 단축키가 아님 | 없는 항목을 고르며 `preventDefault`하지 않습니다 |
| `Cmd`/`Ctrl`/`Alt` 조합은 브라우저의 것 | — |

두 결함이 이 규칙의 이유입니다.

- `Enter`가 typing 검사 **위에서** 처리돼서, `X 폐기`에 포커스한 Enter가 `연결하고 다음`을 실행하고 `preventDefault`로 버튼 본래 동작까지 막았습니다 — 사용자가 손을 뻗은 것과 정반대 동작이 실행됐습니다.
- typing 판정에 `SELECT`와 `isContentEditable`이 없어서, 역할 `<select>`에 포커스를 두고 누른 `x`가 세션을 폐기했습니다. 그때는 폐기에 복구 경로도 없었습니다.

##### 진행 카운터는 살아 있어야 한다

`n / N` 배지는 `role="status"` + `aria-live="polite"` 영역 안에 있고, 옆줄이 `describeBulkAssignProgress(tally, remaining)`(순수)로 `연결 2 · 건너뜀 1 · 폐기 1 · 남은 1개`를 보고합니다. 예전 문구는 `남은 미배정 세션을 하나씩 배정합니다` 고정이었고, 총계는 스냅샷 크기에 얼어 있었습니다 — 세션이 연결·폐기되어 Inbox에서 빠지는 동안에도 화면의 숫자는 이미 없는 큐를 설명했습니다.

세션 헤더에는 `대화 보기`가 있습니다(`onOpenCard` → `App.handleOpenCardById`). 프롬프트 발췌만으로 소속을 판단할 수 없는 경우가 흔한데, Inbox 행에는 있고 **행 없이 배정하는 이 화면에만** 없었습니다.

**선택지의 입력칸은 그 선택지 바로 아래에 렌더합니다.** 제목 입력과 역할 선택은 목록 끝이 아니라 `.bulk-assign-detail` 블록으로 **선택된 옵션 직후**에 들어갑니다. 예전에는 목록 맨 위 `N 새 Work 만들기`를 눌러도 제목칸이 추천 6~9개 아래에 생겨서 스크롤해야 보였습니다. 푸터는 `.kv2-dialog-footer`가 이미 `position: sticky`라 제출 버튼은 항상 보이므로, 입력칸만 올라오면 "누른 자리에서 입력하고 바로 저장"이 성립합니다.

이 때문에 옵션 목록은 `role="listbox"`가 아니라 **`aria-pressed` 토글 그룹**입니다 — listbox의 자식은 option만 허용되므로 입력 블록을 그 안에 끼울 수 없고, 인라인 패널(`works-assign-option`)이 이미 쓰던 관례와도 같아집니다.

인라인 패널의 **추천 Work 목록**(`works-assign-work-list`)도 같은 규칙으로 통일했습니다. `role="listbox"` + `role="option"` 버튼이었는데, listbox는 option만 자식으로 허용하고 `role="option"`을 얹은 버튼은 버튼의 키보드 동작(Tab·Enter·Space)도 option의 목록 탐색도 얻지 못합니다. 지금은 `role="group"` + `aria-pressed` 버튼이라 네이티브 동작이 그대로 살아 있습니다.

#### 색으로 보는 배정 근거 (디렉토리 · 이어진 세션)

배정은 결국 "이 세션이 어느 Work에 속하나" 매칭 게임이라, 근거를 **두 가지 색 신호**로 보여줍니다. 같은 UX가 `⚡ 모두 배정하기` 모달과 Inbox 인라인 패널(= 새 세션이 생겨서 그 자리에서 연결하는 경로) **양쪽에 동일하게** 적용됩니다.

| 신호 | 표시 | 의미 |
|------|------|------|
| **디렉토리 색** | 좌측 6px 색 바 + **디렉토리명에 입힌 배경 틴트** | `projectDir`을 해시해 팔레트 8칸 중 하나에 고정 배정. **같은 색 = 같은 디렉토리** |
| **`같은 디렉토리`** | 그 디렉토리의 텍스트 색 글씨 | 배정 중인 세션과 `projectDir`이 일치 |
| **`🔗 이어진 세션`** | 보라 외곽선 배지 (`--kv2-affinity-chain`) | 이 Work가 **지금 배정하는 세션의 계보에 있는 세션**을 이미 갖고 있음 |

- 색은 세션 쪽 칩(`DirChip`)이 기준 견본이고, 아래 추천 목록의 색이 그것과 같은지만 보면 됩니다. Inbox 행과 Active/Resolved 카드의 `📁` 칩도 같은 색을 씁니다 — 목록 자체가 프로젝트별로 색 그룹이 됩니다.
- 해시는 **경로 전체**로 계산합니다(마지막 세그먼트만 쓰면 서로 다른 체크아웃의 `web/`이 같은 색을 주장합니다). 결정적 문자열 해시(FNV-1a)라 머신·세션이 달라도 같은 색이고 저장할 상태가 없습니다. 팔레트가 8칸이므로 **다른 디렉토리가 같은 색을 받을 수는 있습니다** — 색은 "같음"의 힌트이고 확정은 칩의 디렉토리명입니다.
- **칩은 점이 아니라 이름을 물들입니다.** 예전에는 8~10px 색 점이 이 신호를 혼자 감당했는데, 그 크기는 색조의 표본이 너무 작아 이웃한 두 칸이 같은 점으로 보였습니다. 지금은 디렉토리명 자체에 배경 틴트가 깔립니다. `.works-dir-dot`은 Timeline 라벨에만 남았습니다(그 행은 이미 전체 높이 색 띠를 갖고 있습니다).
- 팔레트는 **색조 45° 등간격 + 이웃 칸 명도 교차**의 두 축입니다. 첫 버전은 8칸 중 3칸이 34° 안의 파랑이라 체크아웃 4개인 머신에서 파란 점 4개가 떴습니다. 보라(`--kv2-affinity-chain`, h 259)는 링을 회전시켜 간격의 정중앙(양쪽 22.5°)에 둡니다 — "같은 색 = 같은 디렉토리"를 깨지 않기 위한 것이니 팔레트를 늘릴 때 이 색조를 침범하지 마세요.
- 토큰은 `kanban-v2.tokens.css`의 **계층 ①(브랜드)** 에 `--kv2-dir-1..8` / `--kv2-affinity-chain`으로 있습니다(다크에서 override하지 않음). **글자에는 스와치를 쓰지 않습니다** — 칸마다 계층 ②의 `--kv2-dir-{n}-text` / `--kv2-affinity-chain-text` 쌍둥이가 있고 이것이 양 테마에서 AA(4.5:1)를 보장합니다. 컴포넌트는 `.works-dir-c{n}`이 실어주는 `--works-dir-accent`(스와치)와 `--works-dir-text`(글자)만 읽고 리터럴 색을 쓰지 않습니다. 자세한 근거는 `docs/design-system.md`의 Works affinity 절.

##### `🔗 이어진 세션` = 세션 계보 (`works.assign_suggest_resume_chain`)

"이어붙인 세션 체인을 추천에 반영"한다는 설정 키가 실제로 하는 일입니다. 계보는 카드의 세 필드에서 나옵니다.

| 필드 | 관계 |
|------|------|
| `parentCardId` | 부모 카드 세션에서 갈라진 subagent 세션 |
| `queuedAfterCardId` | 큐 체인. 단 `continue_queued_after_session`은 같은 `sessionId`를 유지하므로 self-link가 되어 버려집니다 — **새 세션으로 이어진 경우만** 관계가 됩니다 |
| `resumeSessionId` | 이어받으라고 지정된 세션(카드가 결국 다른 세션에 붙은 경우) |

- 계산은 순수 함수 `buildSessionChainMap(cards)`(`src/core/session-chain.ts`) 하나이고 **양방향(대칭)** 으로 기록합니다. triage는 둘 중 미배정인 쪽에서 질문하기 때문입니다.
- **archive된 카드까지 넣어야 합니다.** Inbox에 남는 세션은 이미 끝난 세션이 대부분입니다. 그래서 이 계산은 서버(`computeSessionAggregates`, `includeArchived: true`)에서 하고 결과를 `WorkInboxSession.relatedSessionIds`로 내려줍니다 — 웹의 보드 카드 목록에는 archive된 카드가 없으므로 클라이언트에서 다시 계산하지 마세요.
- **두 집계 경로 모두에서 채워져야 합니다.** `computeSessionAggregates`에는 카드 파생 경로와 네이티브(`aggregateSessionsFn`) 경로가 있고, `plugin/bootstrap.ts`는 **항상** 네이티브 함수를 주입합니다. 예전 코드는 체인 맵을 함수 맨 위에서 계산해두고 `relatedSessionIds`를 카드 파생 분기 **안에서만** 세팅했습니다 — 그래서 운영에서는 이 값이 항상 `undefined`였고, 배지도 계보 우선 정렬도 한 번도 동작하지 않은 채 맵만 10초마다 계산되고 버려졌습니다. 모든 라우트 테스트가 이 인자에 `undefined`를 넘겨 결함이 초록으로 통과했습니다. **계보류 필드는 분기 위에서 한 번 계산해 분기 결과 양쪽에 적용하고, 테스트는 `aggregateSessionsFn`을 주입한 상태로 쓰세요**(`src/__tests__/works-inbox-route.test.ts`).
- **계보는 같은 디렉토리보다 위에 랭크됩니다.** 같은 디렉토리는 "같은 프로젝트"라는 뜻이고, 계보는 "같은 작업 덩어리"라는 뜻입니다. 정렬은 `계보 → 같은 디렉토리 → 나머지`, 각 그룹 안에서 최근 활동순입니다. 둘 다 해당하는 Work는 계보 그룹에 한 번만 들어가고 배지는 둘 다 붙습니다.
- `recommendWorksForSession(session, works, excludeWorkId?, chained?)`의 4번째 인자가 그 집합이고, **넘기지 않으면 예전 동작(같은 디렉토리 우선)과 완전히 동일**합니다. 세션 이동 다이얼로그는 링크에서 세션을 복원해 계보를 모르므로 넘기지 않습니다.
- 설정을 끄면 집합을 아예 계산하지 않으므로 배지도, 재정렬도 없습니다.

### ③ Work 상세 (DialogSkeleton)

제목·상태·기간, 연결된 세션 목록(역할별 + 행마다 `⋯` 메뉴), LLM Summary, 그리고 푸터의 폐기·삭제·완료 액션. Timeline의 바를 클릭해도 같은 다이얼로그가 열립니다(모달은 App의 `openWorkId` 하나만 소유).

레이아웃은 **한 줄에 한 관심사씩 쌓는 세로 스택**입니다: `상태 배지 → Summary → 기간 → 산출물 → 연결된 세션 → 완료 안내 → 푸터`. 예전에는 오른쪽 열에 산출물/타임라인 패널이 따로 있어 왼쪽 세션 목록과 같은 정보가 두 번 나왔는데, 각 관심사가 full-width 한 행을 갖도록 정리했습니다. 새 정보를 넣을 때도 오른쪽 열을 되살리지 말고 행을 추가하세요.

#### 데이터 소스: `GET /api/works/:id/sessions` (보드 카드가 아님)

**산출물 개수와 세션 제목은 보드 카드에서 계산하지 않습니다.** Work를 완료하면 산하 카드가 전부 archive되므로, 보드 목록으로 집계하면 "끝난 일을 되돌아본다"는 이 다이얼로그의 존재 이유가 그대로 무너집니다 — 완료 직후 `카드 0 · done 0`이 되고 세션 제목이 `claude…90` 같은 짧은 세션 id로 주저앉습니다.

- 훅은 `web/src/hooks/useWorkSessions.ts`입니다. **폴링하지 않고** Work의 `updatedAt`이 바뀔 때만 재조회합니다(연결·해제·역할 변경·완료 sweep이 전부 여기에 걸립니다). 다이얼로그가 닫혀 있으면 아무것도 읽지 않습니다.
- **어떤 행이 있는지는 여전히 `work.sessionLinks`가 결정합니다.** 서버 응답은 각 행의 *숫자와 제목*만 공급하므로, 낙관적 연결 해제가 재조회를 기다리지 않고 즉시 행을 지웁니다. 응답이 아직 따라오지 못한 행은 보드 카드로 폴백합니다.
- 응답을 못 받았으면(로딩 중·실패) 예전처럼 보드 카드로 계산하고, 실패는 산출물 행 아래에 "보드에 남은 카드만 세었습니다"로 **정직하게** 알립니다. 조용히 0을 보여주지 않습니다.
- `wiki 문서`는 세 상태를 구분합니다: 실제 경로(`decision='kept'`인 문서 경로) / `생성 대기 중`(`wiki.status='pending'`인 카드가 있음 — 완료 직후는 항상 여기) / `없음`. 예전의 조건 없는 `아직 없음` 고정 문자열은 폐기됐습니다.
- 카드 전부가 보드에서 빠진 세션 행에는 `archived` 표시가 붙습니다.

#### 카드가 사라진 세션 링크 (`cardsMissingAt`)

카드 삭제는 Works에 아무것도 알리지 않았습니다. 그래서 카드를 전부 지운 세션의 링크가 그대로 남고, 세 가지가 조용히 어긋났습니다.

| 증상 | 원인 |
|------|------|
| Timeline 바가 **작업 시작일이 아니라 triage 시각**에서 시작 | `resolveWorkStartedAt`이 카드 없는 링크를 그 링크의 `linkedAt`으로 폴백 |
| 상세의 `대화` 버튼이 사라진 세션을 가리킴 | 링크가 남아 있으므로 행도 남음 |
| 링크가 영구히 잔존 | 제거 경로가 수동 연결 해제뿐 |

지금은 링크에 **스탬프를 찍습니다**(`WorkSessionLink.cardsMissingAt`). 링크를 자동으로 끊지 않는 이유는 **카드 삭제가 soft delete**이기 때문입니다 — `POST /api/cards/:id/restore`로 되돌아오는데, 링크를 자동으로 끊으면 그 세션은 Inbox에도 나타나지 않으므로(카드 없는 세션은 Inbox가 걸러냅니다) 되돌릴 수 있던 동작이 되돌릴 수 없게 됩니다.

| 시점 | 하는 일 |
|------|---------|
| `DELETE /api/cards/:id` / `POST /api/cards/:id/restore` | 그 카드의 세션을 소유한 Work **하나만** 좁혀서 재계산. best-effort — 정리 실패가 카드 쓰기를 실패시키지 않습니다 |
| 서버 부팅 (singleton owner) | 전체 1회 보정. 스탬프가 없던 시절의 데이터가 대상 |
| `POST /api/works/reconcile-links` | 같은 전체 보정의 수동 진입점 |
| `POST /api/works/:id/prune-sessions` | 스탬프가 찍힌 링크를 실제로 제거 (사용자 행동) |

- 판정은 순수 함수 `partitionLinksByCardPresence(work, cards)`(`src/plugin/works/work-links.ts`)이고, 읽기는 `workCardScanFloor` + `timelineArchiveMonths`의 **월 단위 스캔**입니다 — `store.loadArchives()`(전체 스캔)로 바꾸지 마세요.
- 멱등입니다. 스탬프는 매번 카드에서 다시 유도하므로, 변경 없는 데이터에 두 번 돌리면 `marked` / `cleared` 모두 0입니다.
- `discarded`·archive된 Work도 검사합니다. 끊긴 링크는 그쪽 Timeline 바도 똑같이 왜곡합니다.
- 상세 응답이 `WorkSessionSummary.cardsMissingAt`로 내려주고, 그 행이 `.work-session-item--missing`(warn 색)으로 그려지며 경고 문장을 답니다. **`cardCount === 0`으로 판단하지 마세요** — 이 다이얼로그의 카운트는 월 단위로 제한된 읽기라 "창 안에 없음"과 "아예 없음"이 다릅니다.
- 정리는 푸터의 `🧹 끊긴 세션 정리 (N)`이고 `window.confirm`을 거칩니다. **링크가 0개가 돼도 Work는 삭제하지 않습니다** — 정리 버튼에는 목적지가 없으므로(이동은 병합이라 원본을 지웁니다) 레코드·Summary·Timeline 이력을 부수효과로 없애서는 안 됩니다. 비워진 Work는 그대로 보이고 `삭제…`로 지울 수 있습니다.

#### 종료된 Work의 레이아웃

`done` / `discarded` Work는 이미 끝난 기록이므로 다이얼로그가 그렇게 읽혀야 합니다.

| 항목 | `active` | `done` / `discarded` |
|------|----------|----------------------|
| `N일째` 배지·기간 행 | 오늘까지 계속 증가 | **`resolvedAt − startedAt`으로 고정** (완료된 Work가 매일 하루씩 늙지 않습니다) |
| `✅ 완료 시: …` 안내 | 표시 | 숨김 (더 이상 할 수 없는 동작을 설명하는 문장) |
| `폐기…` | 활성 | 비활성 (`이미 종료된 Work입니다`) |
| `✔ 완료 (일괄 archive)` | 활성 | 비활성 (기존 동작) |

날짜 계산은 순수 함수 `workAgeDays(work, now?)`(`worksAssign.ts`) 하나이고, `active` Work의 **종료 예정일은 예측이지 종료가 아니므로** 예정일이 있어도 오늘까지 셉니다. 값이 깨져 있으면 `0일째`가 아니라 최소 1일을 보고합니다.

`기간` 행의 **날짜 입력**이 Timeline 드래그와 짝을 이루는 두 번째 편집 경로입니다.

- `시작`은 항상 편집 가능합니다.
- 타일 라벨은 카드 상세와 같은 영어(`Directory` / `Start` / `End` / `Last activity`)입니다. `End` 라벨은 `active`일 때 **`Planned end`** 로 바뀌고, 값이 있으면 `지우기` 버튼이 함께 나타납니다. `Directory` 타일은 카드 상세의 것을 그대로 씁니다 — 클릭하면 `DirectoryPicker`로 바뀌고 Enter/Save로 저장, Esc로 취소합니다.
- 값을 고르면 즉시 저장합니다. 종료 < 시작이면 PATCH 없이 인라인 오류를 띄웁니다.
- 입력이 빈 값일 때: `active`의 종료 예정이면 **지우기**(`resolvedAt: null`), 그 외에는 타이핑 도중으로 보고 무시합니다.

두 경로 모두 `useWorks`의 **같은 `updateWorkDates`** 를 호출하니 한쪽만 고치지 마세요.

#### 푸터 액션과 Work 삭제

푸터는 왼쪽이 파괴적 영역(`kv2-actions-danger`), 오른쪽이 진행 액션입니다. 왼쪽은 **위험도가 낮은 것부터** 놓습니다.

```
active:  [폐기…]  [삭제…]     [⇉ 다른 Work에 병합…]     [✔ 완료 (일괄 archive)]
종료:    [폐기…(비활성)]  [삭제…]                       (진행 액션 없음)
```

`⇉ 다른 Work에 병합…`은 `active` Work에만 나타납니다(store의 이동 게이트가 archive된
Work의 양쪽 끝을 거부합니다). 파괴적이지 않으므로 왼쪽 danger 그룹이 아니라
`kv2-btn--outline`입니다. 종료된 Work의 푸터에는 진행 액션이 **없습니다** — 비활성 `완료`도,
한때 그 자리에 있던 `↺ 다시 열기…`도 끝난 기록에 다음 행동이 있는 듯 읽혀서 뺐습니다.

두 파괴적 액션은 **버튼 variant로도 위험도를 구분**합니다 — `폐기…`는 `kv2-btn--subtle-danger`
(카드·세션은 그대로, Work만 닫힘), `삭제…`는 `kv2-btn--danger`(레코드 제거). 둘을 같은
`--danger`로 두면 위계가 사라집니다.

`폐기…`와 `✔ 완료 (일괄 archive)`는 **버튼이 곧 실행이 아닙니다.** 둘 다 아래
[완료 / 폐기 확인 다이얼로그](#완료--폐기-확인-다이얼로그)를 열고, 그 다이얼로그가 `'done'`을
돌려줬을 때만 상세 다이얼로그가 닫힙니다. 예전에는 `onComplete(work.id).then(() => onClose())`
였는데, 확인을 거절해도 훅이 PATCH 없이 resolve했기 때문에 **취소가 완료처럼 보였습니다.**

배정 계열 푸터(`WorkAssignInline` / `BulkAssignModal`)도 같은 `kv2-actions-split` 규칙을
따릅니다: 파괴적 액션이 왼쪽 `kv2-actions-danger` 그룹, 진행 액션이 오른쪽
`kv2-actions-primary` 그룹(primary가 맨 오른쪽). `건너뛰기`는 큐를 다음 세션으로
**진행**시키므로 오른쪽입니다.

```
모달:      [X 폐기]                          [S 건너뛰기]  [연결하고 다음 →]
인라인:    [이 세션 무시] [취소]                        ["…"에 연결]
이동:      [⤺ Inbox로 되돌리기] [취소]                  ["…"(으)로 이동]
```

**세 표면의 무시/폐기가 모두 왼쪽 danger 영역, 같은 `kv2-btn--subtle-danger`입니다.**
인라인 패널은 `이 세션 무시`를 primary `연결` **옆 오른쪽 ghost**로 두고 있었습니다 — 같은
행위가 Inbox 행(`kv2-btn--subtle-danger`), 인라인 패널(오른쪽 ghost), 모달(왼쪽 danger)에서
세 가지 위계를 가졌고, 되돌릴 수 없는 액션이 확정 액션 바로 옆에 앉아 있었습니다.

- 인라인 패널의 `취소`는 **같은 왼쪽 그룹 안**에 들어갑니다. `kv2-action-cancel`(`margin-right: auto`)과
  `kv2-actions-primary`(`margin-left: auto`) 사이에 버튼을 두면 푸터 가운데에 떠 버리기 때문입니다
  (`docs/design-system.md`).
- 이동 다이얼로그의 `⤺ Inbox로 되돌리기`는 같은 자리이지만 **파괴적이지 않으므로**(세션은 Inbox로
  복귀) `kv2-btn--outline`입니다 — `secondary.tone`이 위치가 아니라 variant만 고릅니다.

`삭제…`는 `DELETE /api/works/:id`의 유일한 UI 진입점입니다. `폐기`와 달리 Work 레코드 자체가 사라지고, **연결됐던 세션은 Inbox로 복귀**합니다. `deleteWork()`에는 status 가드가 없으므로 `done` Work도 삭제할 수 있고 — 그래서 삭제는 **완료된 Work의 세션을 Inbox로 되돌리는 유일한 경로**입니다. 이 탈출구는 의도적으로 열어두고, 결과를 문구로 정직하게 알립니다(`confirmDeleteWorkMessage()`, 순수 함수 + 유닛 테스트).

| 상태 | 확인 문구 |
|------|-----------|
| `active` / `discarded` | `"<제목>"을 삭제합니다.` + `연결된 세션 N개는 Inbox로 돌아가고, 카드는 보드에 그대로 남습니다.` |
| `done` | `⚠ 완료된 Work를 삭제합니다.` + `연결된 세션 N개가 Inbox로 돌아오지만, 이미 archive된 카드는 복구되지 않습니다.` + `생성된 wiki 문서도 그대로 남습니다.` |

- N은 `work.sessionLinks.length`입니다.
- 삭제는 **되돌릴 수 없으므로 확인을 생략하지 않습니다** — 이동/연결 해제가 확인 없이 실행되고 되돌리기 토스트를 주는 것과 정반대의 취급입니다.
- 성공 시 다이얼로그를 닫고 Work 목록과 Inbox를 함께 갱신합니다(`useWorks.deleteWork`가 `refreshInbox()`까지 수행). 실패하면 다이얼로그를 열어둔 채 상단 에러 배너로 알립니다.
- 확인은 `window.confirm`입니다. **완료·폐기는 예외**로 전용 `DialogSkeleton` 다이얼로그(`WorkResolveConfirmDialog`)를 씁니다 — 완료는 "카드 몇 장이 archive되는가"와 "실행 중 카드가 있는가"를 보여줘야 하고, `window.confirm`은 그 어느 것도 표시할 수 없기 때문입니다. 새 확인 UI가 필요하면 그 컴포넌트를 재사용하세요.

#### 재개 (`POST /api/works/:id/reopen`)

완료는 **일방통행이었습니다.** `PATCH`는 `status: 'active'`를 받아줬지만 그것을 보내는 UI가 없었고, 일괄 archive된 카드는 돌아오지 않았고, `archivedAt`이 계속 찍힌 채였습니다 — 그래서 sweep(멱등 가드)과 세션 이동 게이트가 영구히 닫혔습니다. 유일한 탈출구는 `DELETE`, 즉 레코드를 버리는 것이었습니다.

재개가 하는 일은 정확히 세 가지입니다.

1. `store.unarchiveCards()`로 이 Work의 **archive된 카드를 보드로 복원**합니다.
2. `status: 'active'`, `archivedAt` / `resolvedAt` / `resolution` 제거, `supersededByWorkId` 제거.
3. 그 외에는 아무것도 하지 않습니다 — Summary, 메모, `wikiDocPath`, 세션 링크는 그대로입니다.

**순서가 계약입니다.** 카드 복원이 상태 쓰기보다 **먼저**입니다. 반대로 하면 복원이 실패한 자리에 "카드는 archive에 있는데 `active`인 Work"가 남고, 다음 완료가 `no-cards`를 보고합니다.

| 규칙 | 이유 |
|------|------|
| 복원된 카드는 **`done`으로 돌아옵니다** | 완료 sweep이 전부 `done`으로 바꿨고 **직전 status를 어디에도 기록하지 않습니다.** 없는 정보를 발명하지 않고 정직하게 알립니다(`describeWorkReopen`). 보드의 done 칼럼에 놓이고, 다음 `POST /api/archive`에 다른 done 카드와 똑같이 쓸려갑니다 |
| **큐 자동 dispatch를 트리거하지 않습니다** | 카드 복원은 순수 store 쓰기(`unarchiveCards`)입니다. 작업을 *다시 여는* 행위가 에이전트 실행을 시작해서는 안 됩니다 — 완료 sweep이 `store.updateCard`를 쓰는 것과 같은 이유 |
| **subagent 서브트리가 함께 돌아옵니다** | `archiveCards`가 `parentCardId` 서브트리를 cascade로 가져가므로, 복원도 같은 cascade를 밟습니다. 자식만 archive에 남으면 보드가 그릴 수 없는 분리 상태입니다 |
| 이미 `active`면 `409` | 열려 있는 Work를 "다시 열어" `resolvedAt`(= 종료 예정일)을 지워버리는 사고를 막습니다 |
| `discarded` Work도 재개할 수 있습니다 | 폐기는 카드를 archive하지 않으므로 복원할 것이 없지만(`restoredCardIds: []`), 상태 되돌리기는 똑같이 필요합니다 |

##### wiki 상태 정책 (`unarchiveCards`)

`WikiWorker`는 **archive된** 카드 중 `wiki.status === 'pending'`인 것만 소비합니다. 그래서 복원은 `wiki` 필드를 상태별로 다르게 다룹니다.

| 복원 시점의 `wiki.status` | 처리 | 이유 |
|---------------------------|------|------|
| `pending` | **`wiki`를 지웁니다** | 보드로 나온 카드는 worker가 볼 수 없으므로 그 스탬프는 지킬 수 없는 예약이고, 남겨두면 `archiveCards`가 `!card.wiki`일 때만 스탬프하므로 **다시 archive해도 큐에 들어가지 않습니다** |
| `kept` / `skipped` / `failed` | **그대로 둡니다** | 이미 판정이 끝난 기록입니다. 지우면 다시 완료할 때 같은 문서를 두 번 씁니다(`Work.wikiDocPath` 덮어쓰기는 그대로 동작) |

카드의 `status`는 **건드리지 않습니다** — 위 표의 "`done`으로 돌아온다"가 그 결과입니다.

##### UI

상세 다이얼로그 푸터의 `↺ 다시 열기…` 버튼은 **제거되었습니다**(끝난 Work의 푸터에 진행 액션이 있으면 혼란만 줬습니다). 라우트와 [`WorkResolveConfirmDialog`](#완료--폐기-확인-다이얼로그)의 `reopen` 모드는 남아 있어, 되살릴 때는 진입 버튼만 다시 달면 됩니다.

- 복원 카드 수는 **새 라우트 없이** `GET /api/works/:id/sessions`의 `archivedCardCount`에서 옵니다 — 상세 다이얼로그가 이미 들고 있는 집계이고, 같은 월별 읽기를 두 번 하지 않습니다.
- 그 읽기가 아직 답하지 않았거나 실패했으면 숫자를 **발명하지 않고** 모른다고 말합니다. 복원은 파괴적이지 않으므로 액션 자체는 계속 열려 있습니다.
- 확인 후에도 **상세 다이얼로그는 닫히지 않습니다.** 다시 여는 이유가 그 Work를 계속 보는 것이므로, `active` 레이아웃으로 다시 렌더됩니다(완료/폐기는 `'done'`에서 닫힙니다).
- App은 성공 후 `refreshCards()`를 호출합니다. 3초 보드 폴링이 결국 따라잡지만, 사용자는 카드가 돌아오는 것을 보려고 버튼을 눌렀습니다.

#### 메모 (`Work.notes`)

Work에는 **사람이 쓸 수 있는 자유 텍스트 필드가 없었습니다.** `summary`가 그것처럼 보이지만 아닙니다 — 트랜스크립트에서 LLM이 생성하고 `↻ 다시 생성`마다 통째로 덮어쓰므로, 거기 적은 "락 순서부터 다시"는 다음 재생성에서 사라집니다.

- `notes?: string`, 서버는 **절대 쓰지 않습니다.** `PATCH /api/works/:id`만 씁니다.
- 상한은 `WORK_NOTES_MAX_LENGTH = 4000`자입니다(`src/core/types.ts`). 넘으면 `400`이고 아무것도 저장하지 않습니다. Summary 3~5줄과 한 화면에 같이 놓이는 필드에 무한 문자열을 허용할 이유가 없고, `works.json`은 매 쓰기마다 전체를 직렬화합니다.
- 빈 문자열과 `null`은 같은 뜻입니다(= 메모 없음). 저장된 빈 문자열을 남기지 않습니다.
- **상태 전이와 무관합니다** — 종료된 Work에도 메모를 달 수 있습니다.

UI는 Summary 블록 바로 아래의 `메모` 섹션입니다. 시각적으로 **의도적으로 다르게** 생겼습니다(Summary의 강조 테두리 박스가 아니라, 메모가 없으면 접혀 있는 disclosure 헤딩 + 일반 textarea) — 둘의 차이는 "누가 쓰는 필드인가"이고 그것이 보여야 합니다.

- 제목/디렉토리 인라인 편집과 **같은 draft 센티널 규칙**입니다: `null` = 편집 중 아님. 10초 Works 폴링이 타이핑 중인 텍스트를 덮어쓸 수 없습니다.
- 단 커밋은 **blur가 아니라 명시적 `메모 저장` 버튼**입니다. 여러 줄 메모는 생각하다 다른 곳을 클릭하는 것이 정상이고, blur 커밋이면 문장 절반이 매번 전송됩니다.
- 저장 실패 시 draft를 지우지 **않습니다** — 사용자가 쓴 텍스트를 서버 값으로 조용히 되돌리지 않습니다.
- 저장하지 않은 변경이 있으면 배지로 알리고, **닫기(Esc / ✕ / 배경 클릭) 앞에 확인**을 둡니다. 세 경로 모두 실수하기 쉽고 버려진 메모는 어디서도 복구할 수 없습니다.

#### 완료 / 폐기 확인 다이얼로그

`WorkResolveConfirmDialog`(`DialogSkeleton`) 하나가 두 터미널 전이의 게이트입니다. Works 탭 목록 카드의 `완료…`, Work 상세 푸터의 `✔ 완료 (일괄 archive)`와 `폐기…`가 전부 여기로 들어옵니다.

완료는 이 앱에서 가장 파괴적인 동작입니다(산하 카드 전부 `done` → archive → wiki 파이프라인, 되돌리기 없음). 그래서 **범위를 먼저 말한 뒤** 액션을 제공합니다.

| 표시 | 출처 |
|------|------|
| `카드 N장이 done 처리된 뒤 archive됩니다. 되돌릴 수 없습니다.` | `describeWorkCompletion(preview)` — N은 `sweepCardCount`(보드에 남은 카드) |
| `세션 N` · `카드 M` · `대기 2 · 진행중 1 · done 3` | `preview.sessionCount` / `cardCount` / `describeCompletionByStatus()` |
| `⚠ 실행 중 카드 M장이 있어 완료할 수 없습니다` + 카드 제목 목록 | `preview.runningCardIds` / `runningCardTitles` → 확인 버튼이 **비활성** |
| `⚠ 이미 archive된 Work입니다.` | `preview.alreadyArchived` |
| `⚠ 영향 범위를 불러오지 못했습니다 (…) — 확인 없이 진행하지 않습니다.` | 미리보기 읽기 실패. 확인 버튼은 계속 비활성 |

- 데이터는 [`GET /api/works/:id/completion-preview`](#get-apiworksidcompletion-preview)이며 훅은 `web/src/hooks/useWorkCompletionPreview.ts`입니다. **폴링하지 않습니다** — 다이얼로그가 열려 있는 동안만 한 번 읽고, 서버가 `409`로 거부하면 다시 읽습니다.
- **미리보기가 도착하기 전에는 확인 버튼이 비활성입니다.** 범위를 모르는 상태로 커밋하지 않는 것이 이 다이얼로그의 존재 이유입니다.
- `폐기`는 카드를 건드리지 않으므로 미리보기를 읽지 않습니다(`useWorkCompletionPreview(null)`). 하지만 터미널이고 되돌리기가 없으므로 같은 다이얼로그를 거칩니다 — 문구만 다릅니다.
- `reopen` 모드도 같은 다이얼로그를 씁니다. 되돌릴 수 있는 유일한 전이지만 **카드 한 무더기를 archive ↔ 보드로 옮기고**, `window.confirm`은 몇 장인지 말할 수 없습니다. 확인 버튼 variant만 다릅니다(`kv2-btn--primary` — 유일하게 복원하는 액션이므로 danger도 success도 아닙니다).
- 다이얼로그 제목은 `완료 확인` / `폐기 확인` / `다시 열기 확인`으로 **Work 제목을 넣지 않습니다.** Work 상세 다이얼로그가 제목으로 식별되고 `getByRole('dialog', { name })`이 부분 일치라, 제목을 넣으면 e2e에서 한 셀렉터가 두 다이얼로그를 잡습니다. Work 제목은 본문 첫 줄(`.work-resolve-target`)에 있습니다.

##### 훅 계약: `completeWork` / `discardWork`

```
completeWork(workId, { confirmed: true }) → Promise<'done' | 'declined' | 'blocked'>
```

- **`confirmed` 없이 부르면 아무것도 보내지 않고 `'declined'`** 입니다(`works.done_confirm`이 켜진 동안). 확인 다이얼로그를 잊은 호출자가 얻는 것은 no-op이지 조용한 일괄 archive가 아닙니다.
- 확인 필요 여부는 순수 함수 `requiresDoneConfirm(config)`이며 **설정이 아직 로드되지 않았으면 `true`** 입니다. 예전 게이트는 `config?.doneConfirm`을 직접 읽어서, 설정 요청보다 빠른 클릭이 `undefined`를 "확인 불필요"로 해석했습니다.
- `'blocked'`는 서버 `409`입니다(실행 중 카드, 또는 다이얼로그를 열어둔 사이 상태가 바뀜). 이유는 공용 Works 에러 배너에 있고, 다이얼로그는 닫히지 않습니다.
- 호출부는 **`'done'`일 때만** 자신의 다이얼로그를 닫습니다.

#### 세션 행의 `⋯` 메뉴

연결된 세션 행은 이미 조밀하므로 세션 단위 액션은 `대화` 옆의 `⋯` 하나로 접어둡니다.

| 항목 | 동작 |
|------|------|
| `↪ 다른 Work로 이동…` | 아래 이동 다이얼로그를 엽니다 |
| `🏷 역할 변경 ▸ 개발 / 리뷰 / 디버그` | **전용 API 없이** 같은 Work로의 재연결(`POST /api/works/:id/sessions`)이 역할만 갱신합니다. 오배정의 상당수는 "Work는 맞고 역할이 틀린" 경우라 같은 메뉴에 둡니다 |
| `⤺ 연결 해제 (Inbox로)` | 파괴적이지 않으므로(세션은 Inbox로 복귀) 확인 없이 실행하고 되돌리기 토스트를 띄웁니다 |

역할 3개를 위해 2차 플라이아웃을 띄우지 않고 같은 팝오버 안에서 펼칩니다. 팝오버는 `useAnchoredPopover`(body portal)를 그대로 재사용하므로 다이얼로그의 `overflow`에 잘리지 않고, 외부 pointerdown에 닫히는 것도 그 훅이 이미 처리합니다.

`role="menu"`는 키보드에 대한 약속이라 그만큼을 지킵니다: 열면 **첫 항목에 포커스**, `↑`/`↓`/`Home`/`End`로 항목 이동, `Escape`는 메뉴만 닫고 트리거로 포커스를 돌려줍니다. Escape는 팝오버에서 `stopPropagation()`합니다 — 훅의 Escape 리스너가 `document`에 있어서, 그냥 두면 한 번의 키가 뒤에 있는 Work 상세 다이얼로그까지 함께 닫았습니다. `🏷 역할 변경` 토글에도 `role="menuitem"`이 있습니다(메뉴의 자식 중 유일하게 role이 없었습니다).

#### 세션 이동 다이얼로그

**Inbox 배정 패널(`WorkAssignInline`)을 그대로 재사용합니다.** 배정과 이동은 "이 세션을 어디에 붙일까"라는 같은 질문이고, 추천 랭킹(`recommendWorksForSession`)·제목 자동 제안(`suggestWorkTitle`)·역할 선택이 동일하기 때문입니다. 두 경로가 갈라지면 인라인 패널과 모달의 mutation 분기 문제가 재발합니다. 배정 패널과 다른 점은 셋뿐입니다.

1. 상단 `현재: 🔵 <원본 Work 제목>` 줄
2. 현재 소속 Work를 추천 목록에서 제외 (`recommendWorksForSession(..., excludeWorkId)`)
3. 좌하단 액션이 `이 세션 무시` → `⤺ Inbox로 되돌리기`

패널의 입력 id는 **`useId()`로 생성**합니다. 이 패널은 한 화면에 최대 세 벌(Inbox 행 아래 · 배치 패널 · 이동 다이얼로그)이 동시에 존재할 수 있는데, 고정 id(`works-new-title` / `works-new-role` / `works-link-role`)를 쓰던 동안에는 둘만 열려도 중복 id가 되어 `<label>`이 엉뚱한 컨트롤을 가리켰습니다. e2e도 id 대신 라벨(`getByLabel('새 Work 제목')`)로 접근합니다.

`＋ 새 Work 만들기` 모드는 이동에서도 살아 있습니다("이 세션만 떼어 새 Work로"). 서버에 단일 동사가 없으므로 생성 → 이동 순서로 실행하고, 이동이 실패하면 만들어둔 빈 Work를 되돌려 삭제합니다(`useWorks.moveSessionToNewWork`).

**영향 미리보기**가 확인 버튼 위에 붙습니다. 침묵하고 재계산하면 사용자는 Timeline이 왜 움직였는지 알 수 없기 때문입니다.

```
ℹ 이동 후 "wiki 파이프라인 리팩터링"의 시작일이 8/26 → 8/28로 조정됩니다.
ℹ 마지막 세션이므로 "wiki 파이프라인 리팩터링" Work는 삭제됩니다.
   (이 Work의 Summary도 함께 사라집니다)
```

미리보기는 서버와 같은 순수 함수 `resolveWorkStartedAt()`(`src/plugin/works/work-lifecycle.ts`)에 보드 카드와 이동 후 링크 집합을 넣어 계산합니다 — 규칙을 web에 다시 구현하지 마세요.

#### Work 병합 다이얼로그

`WorkMergeDialog` — `POST /api/works/:id/merge` 앞의 대상 선택기입니다. Work 상세 푸터의 `⇉ 다른 Work에 병합…`이 유일한 진입점입니다.

두 Work가 사실 하나의 일이었다는 것은 흔합니다(오래된 Work가 있는 줄 모르고 새 세션을 새 Work로 배정). 예전에는 그것을 정리하는 방법이 **세션을 하나씩 옮겨 원본을 비우는 것**뿐이었고, 비워진 Work는 서버가 *삭제*하므로 Summary·메모·Timeline 이력이 되돌리기 없이 함께 사라졌습니다.

병합은 [세션 이동 다이얼로그](#세션-이동-다이얼로그)와 **의도적으로 같은 모양**입니다 — 같은 대상 목록, 같은 "확인 버튼 위에 결과를 먼저 말한다" 미리보기, 같은 "거부되면 다이얼로그를 열어둔다" 에러 처리. 단위만 다릅니다(세션 하나가 아니라 Work 전체).

```
ℹ 세션 2개가 "위키 정리"으로 옮겨져 총 3개가 됩니다.
ℹ 이미 "위키 정리"에 있는 세션 1개는 대상의 링크를 그대로 둡니다.
ℹ "위키 정리"의 시작일이 9/5 → 8/28로 조정됩니다.
ℹ "위키 파이프라인"은 폐기(병합됨)로 닫히고, 어디로 합쳐졌는지 기록됩니다.
```

- 미리보기의 시작일도 서버와 **같은 `resolveWorkStartedAt()`** 으로 계산합니다(`describeWorkMergeImpact`, 순수 함수).
- 대상 목록은 `active` Work만입니다(`mergeTargetsFor`). store의 이동 게이트가 archive된/완료 중인 Work의 양쪽 끝을 거부하므로, 종료된 Work를 제시하면 클릭 뒤에 `409`가 기다립니다.
- 자기 자신은 목록에 없고, 서버도 self-merge를 `400`으로 거부합니다.
- 성공하면 상세 다이얼로그가 **대상 Work로 따라갑니다**(`setOpenWorkId(result.to.id)`) — 원본은 살아 있지만 더 이상 작업 중인 Work가 아닙니다.
- 목록·Resolved에서 원본은 `병합됨` 배지와 `M/D → M/D 병합`으로 표시됩니다. `폐기`와 같은 단어를 쓰면 "포기했다"로 읽히는데, 세션은 다른 Work에서 계속 살아 있습니다(`resolvedWordFor`).

#### 결과 토스트 (`WorkSessionNotice`)

이동/해제/역할 변경 **그리고 배정/폐기**의 결과는 화면 하단 토스트로 알립니다. 상태는 **`App`이 소유**합니다 — 원본 Work가 삭제되면 상세 다이얼로그가 닫히므로(`works.find(...) ?? null` 폴백), 그리고 배정하면 그 Inbox 행(과 배정 모달)이 사라지므로, 설명이 그것들보다 오래 살아야 합니다.

- 일반 이동 / 연결 해제 / 역할 변경 → `되돌리기` 제공 (되돌리기도 같은 API를 반대로 호출할 뿐입니다)
- **배정 / 폐기도 `되돌리기`를 제공합니다.** triage가 실제로 하는 두 동작이고 단축키 하나로 실행되는데, 예전에는 되돌리기가 붙은 액션 중 이 둘만 빠져 있었습니다. 되돌리기 구성은 `workAssignNotice.ts`의 빌더 세 개(`noticeForNewWork` / `noticeForLinkedSessions` / `noticeForDiscardedSession`)이고, 인라인 패널·배치 패널·모달이 **같은 빌더**를 씁니다.

| 동작 | 되돌리기 |
|------|----------|
| 새 Work 만들기 (단일 · 배치) | `deleteWork` — 방금 만든 Work를 지우면 연결된 세션이 전부 Inbox로 돌아옵니다(Summary도 `createdAt`도 아직 없으므로 정직한 반대 동작) |
| 기존 Work에 연결 (단일 · 배치) | 연결된 세션만 순차 `unlinkSession`. 서버가 함께 끌고 간 subagent 자손(`cascadedSessionIds`)은 **해제하지 않습니다** — 훅이 그 목록을 돌려주지 않으므로, 자손을 몰래 남기는 되돌리기를 만들지 않고 사실만 알립니다 |
| 폐기 | `restoreIgnoredSession` — 무시 목록에서 제거 |
| 종료된 Work에서 연결 해제 | **되돌리기 없음.** 재연결은 비활성 Work로의 *새* 링크이고 서버가 `409`로 거부합니다. 지킬 수 없는 약속 대신 문장으로 알립니다 |

- 유지 시간은 **30초**입니다(예전 12초). 되돌리려는 액션은 몇 초 *뒤에* 알아차리는 종류입니다.
- 바는 화면 **왼쪽 아래**이고 `pointer-events: none`이며, 자기 버튼만 `.work-session-notice-action`으로 `auto`를 되돌려 받습니다. 가운데(`left: 50%`)에 있을 때는 열려 있는 다이얼로그의 sticky 푸터를 정확히 덮었고 — 배정이 토스트를 띄우게 된 지금은 그 푸터가 바로 모달의 `폐기 / 건너뛰기 / 연결하고 다음` 행입니다 — 클릭을 가리는 것을 넘어 **삼켰습니다**.
- **빈 Work 삭제가 동반된 이동 → 되돌리기를 제공하지 않습니다.** Work를 재생성하면 id가 바뀌고 Summary·`createdAt`은 복구되지 않아 "되돌리기"라는 약속을 지킬 수 없습니다. 대신 이유를 문장으로 설명합니다: `✓ 세션을 "..."으로 옮기고, 비워진 Work "..."를 삭제했습니다.`
- 서버 `409`(다이얼로그를 열어둔 사이 대상이 완료됨)는 다이얼로그를 닫지 않고 서버 메시지를 그대로 인라인 표시합니다.

Works 탭 헤더의 `⚙ 설정` 토글. 아래 `works.*` 키를 편집합니다. wiki의 LLM 설정과는 완전히 독립입니다.

### ⑤ Timeline (Board 탭의 뷰)

**Timeline은 탭이 아니라 Board 탭의 세 번째 뷰입니다.** 헤더의 `리스트 │ 보드 │ 타임라인` 토글로 전환합니다(ClickUp과 같은 구조). 예전에는 최상위 탭이었는데, Board가 이미 가진 작업을 다른 각도로 보여주는 것뿐인데도 별도 섹션처럼 읽혔습니다. `MainTab`에 `'timeline'`을 되살리지 마세요 — 선택값은 `boardViewMode`(localStorage `kanban-board-view-mode`)에 있습니다.

**열 = 하루, 행 = 세션.** 이 두 개가 모델의 뼈대입니다.

- **시간 최소 단위는 하루입니다.** 이 보드의 카드 중 절반은 3분 안에 끝나는데, 시/분 축으로 그리면 전부 보이지 않는 실선이 됩니다. 3분 카드도 하루 칸 하나를 차지합니다(ClickUp도 시간 단위 표현이 없습니다).
- **행 최소 단위는 세션입니다.** 모든 카드는 세션에 속하므로 카드만 떠 있는 행은 매달릴 곳이 없습니다. 카드는 세션 행 **안의 날짜 칸**(`.tl-day`)으로만 그려집니다.
- **실행된 것만 보입니다.** 카드는 `startedAt`(없으면 `completedAt`)부터 등장하고, 생성일은 쓰지 않습니다. `todo`로 두 달 방치된 카드가 화면을 가로지르는 바를 만들지 않게 하려는 것이고, 예약(고스트) 바도 그리지 않습니다.
- **미배정 세션도 보입니다** — `미배정` 배지가 붙고, 같은 디렉토리 그룹의 Work들 **뒤에** 최근 순으로 놓입니다. 행의 `배정` 버튼은 세션 하나를 담은 배정 모달을 열고, 배정되면 다음 폴링에서 그 Work 아래로 들어갑니다. (예전 문서의 "미배정 세션은 타임라인에 나타나지 않습니다"는 폐기된 규칙입니다.)
- **폐기한 세션은 `폐기` 배지만 갖고 `배정` 버튼이 없습니다.** 그 세션도 실제로 실행됐으므로 행은 남지만, Inbox에서 빠졌으므로 배정 모달이 열 대상이 없습니다 — 예전에는 `미배정 · 배정`이 그대로 떠 있고 `handleAssignSession`이 Inbox에서 못 찾으면 조용히 `return`해서 **버튼이 영구히 무반응**이었습니다. 라우트가 `TimelineSessionSpan.ignored`로 내려주고(`/api/timeline`이 `ignoredSessionIds`를 읽습니다), 그래도 대상을 못 찾은 배정 시도는 이제 에러 배너로 이유를 말합니다.
- **서브에이전트 카드는 기본 숨김**입니다(`subagents=1` / 헤더 체크박스, localStorage `kanban-timeline-subagents`).
- **디렉토리 필터**(`.tl-dir-filter` 칩)로 한 프로젝트만 볼 수 있습니다. Board 탭의 `BoardProjectSwitcher`는 카드 컬럼용이라 타임라인 모드에서 숨겨지고, 그래서 예전에는 바쁜 그리드를 좁힐 방법이 그룹 접기밖에 없었습니다. 옵션은 **그리드 자신의 디렉토리 그룹**(`timelineDirOptions(rows)`)에서 만들므로 카드가 전부 archive된 프로젝트도 필터에 나옵니다. 선택은 `filterTimelineRows(rows, groupKey)`로 적용되고, 옵션 목록은 **필터 전 rows**에서 뽑습니다 — 아니면 한 디렉토리를 고른 순간 나머지 옵션이 사라집니다.
- **범례는 실제 그려진 것만** 담습니다(`timelineLegend(rows)`). 고정 6칸 목록이던 시절엔 `대기` 스와치가 늘 떠 있었는데, 실행된 카드만 그리드에 들어오므로 그 색은 거의 나타나지 않습니다 — 가리킬 대상이 없는 범례 항목은 뷰의 모델을 잘못 가르칩니다. 라벨은 `TIMELINE_STATUS_LABELS`로 통일했습니다: `대기` / `진행중` / **`검토 대기`**(`complete`) / `완료`(`done`). `complete`를 `검토 대기`로 부르는 이유는 그 색이 보드의 분홍-빨강(`--kv2-status-complete-accent`)이라 **실패로 읽히기** 때문입니다 — 색은 보드가 소유하므로 그대로 두고(`docs/design-system.md`), 라벨이 "에이전트는 끝났고 사람 확인을 기다린다"는 실제 의미를 말합니다. 예전 범례는 `완료`(빨강)와 `Done`(초록)을 한 줄에 섞어 한 화면에서 두 언어로 상태를 불렀습니다.
- **읽는 법 안내는 처음 한 번만** 뜨고(localStorage `kanban-timeline-help-seen`) 그 뒤로는 툴바의 `?` 버튼 뒤에 있습니다. 예전에는 5줄 각주가 모든 그리드 아래에 상주했습니다.
- **불러오지 못하면 그리드를 흐리게** 하고(`.timeline--errored`) 빈 상태 문구도 "불러오지 못해 비어 있습니다"로 바뀝니다. 에러 배너 문구는 순수 함수 `describeTimelineError(raw)`가 만듭니다 — 예전에는 라우트 원문(`Not found`)이 그대로 떴고, 그리드는 세션 0개로 정상 렌더돼서 둘이 합쳐 **"이번 주엔 아무것도 안 돌았다"** 로 읽혔습니다.

행 계층은 **디렉토리 → Work → 세션**입니다. ClickUp이 왼쪽에 사람을 두는 자리에 이 프로젝트는 디렉토리를 둡니다. Work의 그룹은 자기 `projectDir`이고, 없으면 보이는 세션들의 다수 디렉토리를 씁니다 — **Work가 세션을 소유하므로 한 Work의 행들이 두 그룹으로 쪼개지지 않습니다.** 디렉토리가 없는 것들은 맨 아래 버킷으로 모입니다.

Work 행은 두 가지를 동시에 가집니다: 드래그로 편집하는 **계획 바**(`.tl-bar`)와, 그 아래 세션 행들의 **실측 레일**(`.tl-rail`).

- 미완료(`active`) Work의 바는 **오늘 열까지 연장**되고 오른쪽 끝이 점선으로 열려 있습니다(`▸ 진행중`). 단 종료 예정일을 찍어두면 그 날에서 끝납니다(`▸ M/D 예정`).
- 완료/폐기된 Work의 바는 `startedAt → resolvedAt`에 고정됩니다. **`resolvedAt`이 없으면(손상된 레코드) 오늘까지 그립니다 — `updatedAt`으로 대체하지 않습니다.** 예전 폴백은 종료된 Work의 제목만 고쳐도 바가 하루씩 늘어나게 만들었습니다. 터미널 전이는 항상 `resolvedAt`을 스탬프하므로(`docs/invariants.md`) 이 경로에 오는 건 데이터가 깨진 경우뿐이고, 그때는 그럴듯하게 보이는 것보다 눈에 띄는 게 낫습니다. `· M/D 폐기` 주석도 같은 이유로 실제 `resolvedAt`만 씁니다(없으면 `· 폐기`).
- 조회 범위를 벗어난 시작/종료는 `◂ M/D부터` / 점선 보더로 표시됩니다(세션 레일도 같은 규칙). **월간 뷰에서도 유지되고, 축약형(`◂8/20`, `▸9/5`)으로 렌더됩니다** — 예전에는 CSS가 월간에서 이 힌트를 `display: none` 처리해서, 월간 그리드가 모든 바를 "그려진 그대로 시작하고 끝났다"고 주장했습니다. 폐기 주석과 세션 칩만 월간에서 숨습니다.
- 세션이 이 기간에 하나도 실행되지 않아도, Work 바가 기간에 걸쳐 있으면 Work 행은 남습니다("열려 있는데 이번 주엔 아무것도 안 돌았다"는 정보).
- 클릭 대상: 날짜 칸에 카드가 하나면 **카드 상세**, 여러 장이면 **세션 대화**. 세션 레일 → 세션 대화. Work 바 → Work 상세.

색은 **네 층을 서로 다른 축에 올려** 충돌을 피합니다. 자세한 규칙은 `docs/design-system.md`의 Timeline 절을 보세요.

| 층 | 색 | 왜 |
|----|----|----|
| 디렉토리 | 8색 해시 팔레트(`--kv2-dir-1..8`, 왼쪽 색 띠) | Works 탭과 같은 색 = 같은 프로젝트 |
| Work 바 | 먹색(`--kv2-timeline-work-bar`) | 계획이라서. 색 예산은 카드 상태에 씁니다 |
| 세션 레일 | 보라(`--kv2-affinity-chain`) | 어떤 카드 상태도 쓰지 않는 색 → 레일이 상태로 오해되지 않습니다 |
| 카드 날짜 칸 | 보드의 상태 색(대기 파랑 / 진행중 노랑 / 완료 빨강 / done 초록) | 보드와 같은 의미를 같은 색으로 |

주간(월~일 7열)과 월간(그 달을 덮는 월~일 정수 주, 28~35열)을 토글합니다.

차트/캘린더 라이브러리를 쓰지 않고 단일 CSS grid로 그립니다. 순수 로직은 두 모듈로 나뉘어 있고 둘 다 유닛 테스트가 있습니다:

| 모듈 | 책임 |
|------|------|
| `web/src/components/Works/timelineModel.ts` | 날짜 기하 — 범위, 열 인덱스, Work 바, 드래그 리사이즈, 라벨 폭 |
| `web/src/components/Works/timelineRows.ts` | 행 모델 — 디렉토리/Work/세션 그룹핑, 실측 span clamp, 카드 → 날짜 칸 버킷팅 |

`TimelineView.tsx`는 렌더와 포인터 처리만 합니다. 새 기하 규칙은 `timelineModel.ts`, 새 그룹핑 규칙은 `timelineRows.ts`에 추가하세요.

#### 데이터: `GET /api/timeline`

Works 폴링만으로는 부족합니다 — 그리드는 **이미 아카이브로 넘어간 카드**를 그려야 하기 때문입니다. 그래서 창(window)을 받는 전용 엔드포인트가 있고, 그 창이 아카이브 읽기를 제한하는 장치입니다.

- `store.loadArchives()`(전체 아카이브 스캔)는 **건드리지 않습니다.** `listArchiveMonths()` + `loadArchiveMonth()`를 조합할 뿐이므로 wiki/Telegram의 전체 스캔 경로는 그대로입니다.
- 읽을 월은 `timelineArchiveMonths()`가 고릅니다: 아카이브 파일은 `updatedAt` 기준으로 묶이고 카드는 실행보다 먼저 갱신될 수 없으니, **창의 월 −1개월 이상인 월 전부**면 충분합니다(−1은 KST/UTC 월경계 보정). 이번 달 창이면 파일 2개만 읽습니다.
- 응답에는 **Work 그룹핑이 없습니다.** 웹은 이미 `/api/works`를 폴링하므로 세션 → Work 매핑을 클라이언트가 합니다. 그래야 낙관적 배정이 재조회를 기다리지 않고 즉시 재그룹됩니다.
- 훅은 `web/src/hooks/useTimeline.ts`(10초 폴링). 창이 바뀌면 재조회하고, 방금 떠난 창의 늦은 응답은 버립니다.

#### 라벨 열 너비 조정

왼쪽 `프로젝트 · 세션` 라벨 열은 고정폭이 아니라 사용자가 늘이고 줄입니다. 제목이 긴 행이 `…`로 잘리면 헤더 오른쪽 경계의 그립(`.tl-label-resizer`)을 잡아끄면 됩니다.

| 조작 | 동작 |
|------|------|
| 드래그 | 포인터 x − 헤더 라벨 셀의 좌측 좌표 = 새 너비. 라벨 열이 `position: sticky`라 월간 뷰를 가로 스크롤한 상태에서도 기준점이 맞습니다 |
| `←` / `→` | `LABEL_WIDTH_STEP`(16px) 단위 |
| 더블클릭 / `Home` | `DEFAULT_LABEL_WIDTH`(240px)로 복구 |
| 범위 | `clampLabelWidth()`가 120~560px로 clamp. 손상된 저장값·`NaN`은 기본값으로 |

기본값은 180px이 아니라 **240px**입니다 — 180px에서는 한글 Work 제목이 여덟 자쯤에서 `…`로 잘려서, 실제 보드의 기본 화면이 잘린 제목 열이 됐습니다. 좁은 화면에서는 CSS가 `--tl-label-cap`으로 이 값을 **덮지 않고 상한만** 걸어줍니다(인라인 스타일은 스타일시트가 이길 수 없으므로, 그리드 트랙은 `min(--tl-label-width, --tl-label-cap)`인 `--tl-label-track`을 읽습니다). `Timeline.css` 끝의 미디어 쿼리가 900px/480px에서 상한과 `--tl-col-min`을 낮추고, 480px 이하에서는 가로 스크롤 안내를 노출합니다.

너비는 `--tl-label-width`를 `.timeline`에 **인라인**으로 얹어 적용합니다(CSS의 `180px`는 기본값일 뿐). `localStorage`의 `kanban-timeline-label-width`에 저장되어 새로고침 뒤에도 유지되고, 저장 실패(사생활 보호 모드·용량 초과)는 조용히 무시합니다. 열이 넓어지면 날짜 열은 `--tl-col-min`까지 좁아지고 그 아래로는 `.tl-scroll`이 가로 스크롤합니다 — 바의 열 배치는 그대로입니다.

#### 바 끝 드래그로 날짜 조정

바에 마우스를 올리면 양 끝에 손잡이(`.tl-bar-handle`)가 나타납니다. 잡아끌면 미리보기가 열 단위로 따라오고(`8/31 → 9/3` 칩), 놓는 순간 그 날짜로 `PATCH /api/works/:id`를 보냅니다.

| 규칙 | 동작 |
|------|------|
| 왼쪽 손잡이 | `startedAt` 변경 |
| 오른쪽 손잡이 | `resolvedAt` 변경. **`active` Work에서도 동작합니다** → [종료 예정일](#종료-예정일-active-work의-resolvedat) |
| 바 뒤집기 | 불가능. `resizeBar()`가 반대편 끝으로 collapse시킵니다(하루짜리 바) |
| 키보드 | 손잡이를 **클릭하거나** Tab으로 포커스한 뒤 `←` / `→` → 하루씩 이동 후 즉시 저장 |
| 열이 안 바뀐 드롭 | PATCH를 보내지 않습니다 (드래그 없는 클릭이 쓰기를 유발하지 않도록) |
| 편집 후 | `WorkSessionNotice` 토스트로 무엇이 바뀌었는지 알리고 **되돌리기**를 제공합니다(30초) |

**손잡이 `pointerdown`은 `preventDefault()` 뒤에 `focus()`를 명시적으로 호출합니다.** pointer capture를 잡으려면 `preventDefault()`가 필요하고, 그것이 `tabIndex` 요소의 암묵적 포커스까지 없앱니다 — 그래서 문서가 말하는 "손잡이에 포커스를 두고 `←`/`→`"가 **Tab으로만** 도달 가능했고, 손잡이를 클릭한 직후 `→`를 누르면 포커스가 `월간` 버튼으로 넘어갔습니다.

##### 잘린 바의 편집은 **raw 컬럼** 기준입니다

`TimelineBar`는 그려지는 컬럼(`startIndex`/`endIndex`, clamp됨)과 **실제 컬럼**(`rawStartIndex`/`rawEndIndex`, 음수·범위 초과 가능)을 함께 들고 있습니다. 렌더는 clamp된 값을, **편집은 raw 값을** 씁니다.

- 8/20에 시작한 Work를 9/1 주간에서 보면 바는 컬럼 0에 그려지지만 `rawStartIndex`는 `-11`입니다. `→`는 `-11 + 1 = -10` → `8/21`로 저장합니다.
- 예전에는 clamp된 `0 + 1` → **`9/2`** 로 저장했습니다. 되돌리기도 없이 거의 2주가 앞으로 밀렸습니다.
- 뒤집힘 가드(`resizeBar`)도 raw span 기준입니다. clamp된 span은 그 바의 기하가 아닙니다.
- 손잡이의 `aria-valuenow`/`aria-valuetext`도 raw 값을 읽으므로, 스크린리더가 8/20 시작을 `9/1`로 읽어주지 않습니다.
- 드래그는 반대로 **드롭한 눈에 보이는 컬럼**을 그대로 씁니다(사용자가 그 자리에 놓았으므로). 열이 안 바뀐 드롭은 드래그 origin과 비교해 걸러냅니다.

날짜는 **일 단위**로만 바뀝니다. 다만 시:분:초 처리는 시작과 종료가 다릅니다.

| | 저장되는 시각 | 이유 |
|---|---|---|
| 시작 (`startedAt`) | 원본의 시:분:초 유지 (`isoForColumn`) | 첫 카드의 실제 시작 시각이라는 실체가 있음. 예: `8/31 14:20` → 9/3 열로 드래그 → `9/3 14:20` |
| 종료 (`resolvedAt`) | 그 날의 **끝** `23:59:59.999` (`endIsoForColumn`) | 사용자가 찍은 종료일은 "이 날까지 진행했다"는 뜻이고 이어받을 실제 시각이 없음(active Work엔 `resolvedAt` 자체가 없음). 게다가 `updatedAt` 같은 임의 시각을 빌리면 `시작 9/1 14:00` + `종료 9/1 09:00`처럼 하루짜리 바가 역전 instant가 되어 store에 거부됨 |

> 자동 stamp(진짜 완료 시각)는 이 규칙과 무관하게 그 순간을 그대로 기록합니다. 손으로 찍은 날짜에만 end-of-day가 적용됩니다.

바 자체는 `<button>`(클릭 → Work 상세)이라 손잡이를 자식으로 넣을 수 없습니다. 그래서 grid 배치는 래퍼인 `.tl-bar-slot`이 갖고, 바와 손잡이는 그 안에서 형제입니다 — e2e에서 열 좌표를 읽을 때는 `.tl-bar`가 아니라 `.tl-bar-slot`을 봐야 합니다.

드래그는 window 리스너가 아니라 손잡이의 **pointer capture**로 돕니다(`setPointerCapture` → `onPointerMove` / `onLostPointerCapture`). `pointerdown` 안에서 동기적으로 잡히기 때문에 "눌렀는데 아직 리스너가 안 붙은" 구간이 없고, 포인터가 12px 손잡이를 벗어나도 계속 추적됩니다. 종료 신호는 `lostpointercapture` **하나만** 씁니다 — `pointerup`도 같이 듣으면 같은 preview를 두 번 커밋합니다.

포인터 기하는 헤더 셀의 `data-tl-col` 속성에서 측정합니다(`measureColumns`). 헤더에서 이 속성을 지우지 마세요. **측정은 드래그 시작 시 1회**만 하고 `metricsRef`에 캐시합니다 — 예전에는 매 `pointermove`마다 `querySelector` 2번 + `getBoundingClientRect` 2번(강제 레이아웃)을 돌렸습니다. 드래그 중에 열이 움직일 수는 없습니다: 범위 변경은 드래그를 중단시키고, 포인터가 capture된 동안 가로 스크롤도 발생하지 않습니다.

##### 렌더 성능은 계약입니다 (memo + 격리된 드래그 상태)

행은 4개의 memo 컴포넌트로 그립니다: `DirRowView` / `WorkRowView` / `SessionRowView`, 그리고 그 안의 `RowCells`. 이들은 **하나의 참조 안정한 `TimelineHandlers` 번들**을 공유합니다.

- 드래그 중 상태는 `dragRef`(ref)에 있고, React가 알아야 하는 것(`{ workId, preview }`)만 state입니다. 그래서 **컬럼을 넘을 때만** 리렌더가 일어나고, 그때도 `dragPreview`가 바뀌는 건 드래그 중인 Work 행 하나뿐입니다.
- 예전에는 `setDrag`가 매 `pointermove`마다 `TimelineView` 전체를 리렌더했고 자식 중 memo인 것이 하나도 없었습니다 — 월간 35열 × ~60행이 통째로 다시 그려졌습니다.
- 번들이 참조 안정해야 memo가 실제로 bail out합니다. `App`은 매 렌더마다 새 인라인 화살표 함수를 내려주므로, 콜백 props는 `latest` ref를 거쳐 들어오고 wrapper는 한 번만 만듭니다. **새 콜백은 이 번들 안에 넣으세요.**

#### 종료 예정일 (active Work의 `resolvedAt`)

`active` Work도 `resolvedAt`을 가질 수 있습니다. 완료 처리 전에 "이 날쯤 끝난다"를 먼저 찍어두는 용도입니다.

- **없으면** 바가 오늘까지 이어지고 `▸ 진행중`이 붙습니다 (기존 동작).
- **있으면** 바가 그 날에서 끝나고 `▸ M/D 예정`이 붙습니다. 상태는 여전히 `active`이므로 오른쪽 끝은 점선으로 열려 있습니다.
- 예정일이 **과거**여도 바를 오늘까지 다시 늘리지 않습니다. 직접 조작한 위치가 곧 화면이어야 하기 때문입니다. 대신 바가 warn 색으로 바뀌고 `▸ 예정 N일 초과`를 붙입니다 — [예정일 초과](#예정일-초과-예정-n일-초과).
- **비우면** 다시 오늘까지 이어집니다 (`resolvedAt: null`). 상세 다이얼로그의 `예정일 지우기` 버튼, 또는 날짜 입력을 비우면 됩니다.
- 나중에 **완료 처리하면 이 날짜가 그대로 종료일이 됩니다** — `updateWork`의 자동 stamp는 `resolvedAt`이 비어 있을 때만 `now`를 찍기 때문입니다. 사용자가 "날짜부터 정하고 나중에 완료" 순서로 일할 수 있는 근거가 이 규칙입니다.
- 단, `status: 'active'`로 **되돌리면** `resolvedAt`은 지워집니다([재개](#재개-post-apiworksidreopen)도 같습니다). 재개된 Work의 예정일은 다시 찍어야 합니다.

## API 레퍼런스 (`/api/works*`)

전체 규칙(에러 형식, CORS, 인증)은 [`api-reference.md`](./api-reference.md)와 동일합니다. `workStore`가 서버에 주입되지 않은 환경에서는 모든 엔드포인트가 `503 Works not available`을 반환합니다.

### `GET /api/works`

Work 목록을 반환합니다. 기본 순서는 `updatedAt` 내림차순입니다.

쿼리:

- `status=active|done|discarded` (선택) — 잘못된 값은 `400 Invalid status`
- `projectDir=<절대경로>` (선택) — **정확 일치**(접두/접미 일치가 아닙니다)
- `q=<문자열>` (선택) — 제목 · `projectDir` · `notes` · `summary.lines`를 대소문자 무시 부분 일치. 공백만이면 필터로 취급하지 않습니다
- `sort=updated|stale|planned` (선택, 기본 `updated`) — 잘못된 값은 `400 Invalid sort`. 조용히 기본 순서로 돌아가지 않습니다

| `sort` | 순서 |
|--------|------|
| `updated` | `updatedAt` 내림차순 (최근 활동 먼저) |
| `stale` | `updatedAt` 오름차순 (가장 오래 방치된 것 먼저) |
| `planned` | `resolvedAt` 오름차순, **예정일 없는 Work는 전부 뒤로**(그 안에서는 `updated` 순) |

모든 비교자는 `id` 비교로 끝나 **전순서**입니다 — 타임스탬프가 같은 두 Work가 요청마다 자리를 바꾸지 않습니다. 파싱 불가능한 날짜는 던지지 않고 뒤로 가라앉습니다.

필터·정렬 규칙은 순수 함수 `selectWorks()`(`src/core/work-list.ts`) 하나이며 **웹 Active 목록이 같은 함수를 씁니다** — [Active 목록의 검색 · 필터 · 정렬](#active-목록의-검색--필터--정렬).

### `POST /api/works`

Work를 생성합니다. 항상 `status: 'active'`로 시작합니다.

```json
{ "title": "Works 탭 구현", "projectDir": "/Users/me/workspace/agent-kanban", "startedAt": "2026-09-01T03:00:00.000Z" }
```

- `title` (required, 공백만이면 `400`)
- `projectDir` (선택)
- `startedAt` (선택, 기본값 = 생성 시각)

`201`로 생성된 `Work`를 반환합니다.

### `GET /api/works/:id`

단일 Work. 없으면 `404 Work not found`.

### `PATCH /api/works/:id`

`WorkPatchInput`을 받습니다: `title`, `status`, `resolution`, `projectDir`, `startedAt`, `resolvedAt`, `summary`, `notes`, 그리고 라우트 전용 플래그 `confirmArchive`.

- `notes`는 `string | null`이고 상한은 `WORK_NOTES_MAX_LENGTH = 4000`자입니다. 타입이 틀리면 `400 notes must be a string or null`, 길이를 넘기면 `400 notes must be at most 4000 characters`이며 **아무것도 저장하지 않습니다.** `''`와 `null`은 같은 뜻(= 메모 없음)이고, 상태를 건드리지 않으므로 종료된 Work에도 쓸 수 있습니다 — [메모](#메모-worknotes).
- **`archivedAt`, `wikiDocPath`, `supersededByWorkId`는 서버 소유이며 patch로 받지 않습니다**(`400`). `supersededByWorkId`는 merge만 씁니다. 같은 이유로 `resolution: 'superseded'`도 `400 Invalid resolution`입니다 — 짝이 되는 포인터 없이 쓰면 아무 곳도 가리키지 않는 `병합됨` Work가 됩니다. `archivedAt`은 sweep의 idempotence와 세션 이동 게이트를 동시에 결정하므로, 임의 문자열이 들어가면 두 경로가 되돌릴 UI 없이 영구히 막혔습니다.
- 모든 필드는 타입 검증을 거칩니다. `{"title": 7}`은 `400 title must be a string`이지 `400 .trim is not a function`이 아닙니다 — 내부 스택 조각이 사용자 문구가 되어서는 안 됩니다.
- 날짜는 `new Date(v).toISOString()`으로 **UTC `Z` 정규화**해 저장합니다. `+09:00` 오프셋 표기는 같은 순간의 `Z` 표기보다 문자열로 뒤에 정렬되므로, 정규화하지 않으면 `startedAt` clamp가 잘못 동작합니다.

- 완료로 새 카드가 archive되면 라우트가 `wikiWorker.kick()`을 호출합니다 — 다음 60초 주기를 기다리지 않습니다.
- `status: 'done'`은 **산하 카드 일괄 done → archive** 부수효과를 함께 실행합니다. 카드 전이는 `store.updateCard`(순수 store 쓰기)를 쓰기 때문에 큐 자동 dispatch를 트리거하지 않습니다 — 작업을 닫는 행위가 새 에이전트 실행을 시작해서는 안 되기 때문입니다.
- **실행 중 카드가 있으면 `409 { error, runningCardIds }`** 로 거부하고 상태 전이도 기록하지 않습니다.
- `works.done_confirm`(기본 `true`)이 켜져 있으면 `confirmArchive: true`가 함께 오지 않는 한 상태 전이만 기록하고 sweep은 보류합니다. 그 상태(= `done`인데 `archivedAt` 없음)의 Work는 **`status` 없이 `{ confirmArchive: true }`만** 보내도 sweep을 끝낼 수 있고, 그 동안은 세션 이동이 `409`로 거부됩니다.
- 반복된 `done` PATCH는 `archivedAt`이 이미 찍혀 있으면 재sweep하지 않습니다(idempotent). 판정과 스탬프가 `WorkStore.claimArchiveSweep()` 한 락 구간에 있으므로 동시 두 건도 archive를 한 번만 실행합니다.
- 응답은 `WorkPatchResponse`(= `Work` + `sweep` 리포트)이며 `sweep.failed[]`가 부분 실패를 그대로 보고합니다 — 자세한 필드는 [`api-reference.md`](./api-reference.md#patch-apiworksid) 참고.
- `status: 'active'`로 되돌리면 `resolvedAt` / `resolution`이 지워집니다.
- `startedAt` / `resolvedAt`만 담긴 **날짜 전용 PATCH**(바 끝 드래그, 상세 다이얼로그의 날짜 입력)는 상태를 건드리지 않으므로 완료 부수효과가 전혀 걸리지 않습니다. `active` Work에 `resolvedAt`을 넣는 것도 이 경로이며(종료 예정일), `resolvedAt: null`이 그것을 지웁니다. 파싱 불가능한 값은 `400`이고, 결과가 `resolvedAt < startedAt`이 되는 편집도 `400`입니다 — 단, 호출자가 날짜를 명시한 경우에만 검사하므로 이미 뒤집혀 저장된 레코드도 다시 고칠 수 있습니다.

### `POST /api/works/:id/reopen`

`done` / `discarded` Work를 `active`로 되돌리고 일괄 archive된 카드를 보드로 복원합니다. 본문 없음.

```json
{ "work": { "id": "...", "status": "active" }, "restoredCardIds": ["..."], "scannedMonths": ["2026-08", "2026-09"] }
```

- 이미 `active`면 `409 Work is already active: "<제목>"`이고 아무것도 쓰지 않습니다. 없으면 `404`.
- **카드 복원이 상태 쓰기보다 먼저입니다.** 순서와 wiki 상태 정책, 복원 카드의 status는 [재개](#재개-post-apiworksidreopen)에 있습니다.
- `scannedMonths`는 실제로 파싱한 archive 월 파일입니다(`workCardScanFloor(work)` 기준). 전체 archive 스캔을 하지 않습니다.
- **큐 자동 dispatch를 트리거하지 않습니다.**

### `POST /api/works/:id/merge`

이 Work의 세션을 다른 Work로 옮기고, 이 Work를 `병합됨`으로 닫습니다.

```json
{ "intoWorkId": "wrk_..." }
```

```json
{ "from": { "status": "discarded", "resolution": "superseded", "supersededByWorkId": "wrk_to" },
  "to": { "sessionLinks": [ ... ] },
  "movedSessionIds": ["..."], "skippedSessionIds": ["..."] }
```

- `intoWorkId`가 없거나 문자열이 아니면 `400 intoWorkId is required`, 자기 자신이면 `400 Cannot merge a work into itself`, 대상이 없으면 `404`.
- 양쪽 중 **하나라도 이미 archive됐거나 완료 중이면 `409`** 입니다(세션 이동과 같은 게이트).
- 링크는 `linkedAt`과 `role`을 그대로 갖고 이동합니다. **대상이 이미 갖고 있는 세션은 건너뜁니다**(`skippedSessionIds`) — 살아남는 쪽의 링크와 역할을 조용히 덮어쓰지 않습니다. 1:N 불변식(한 세션은 정확히 한 Work)이 유지됩니다.
- 대상의 `startedAt`은 **락 안에서** 병합 후 링크 집합으로 재계산합니다(`WorkStartedAtResolver`, 다른 링크 변경 경로와 같은 계약).
- 원본은 **삭제되지 않습니다**: `status: 'discarded'` + `resolution: 'superseded'` + `supersededByWorkId`. Summary·메모·Timeline 이력이 남고, 목록이 "어디로 갔는지"를 말할 수 있습니다. 마지막 세션을 옮겨 Work를 비우는 경로(`PATCH /api/works/sessions/:sessionId`)는 여전히 원본을 *삭제*하므로 구별하세요.
- 원본을 [재개](#재개-post-apiworksidreopen)하면 `supersededByWorkId`가 지워집니다 — 세션은 대상에 남아 있으므로 포인터만 무효가 되기 때문입니다.

### `DELETE /api/works/:id`

`204`. Work만 삭제되며 카드는 그대로입니다(완료된 Work였다면 archive 상태도 그대로). 연결돼 있던 세션은 다시 Inbox로 돌아옵니다. **status 가드가 없습니다** — `done` Work도 삭제되며, 그것이 완료된 Work의 세션을 Inbox로 되돌리는 유일한 경로입니다. UI 진입점은 Work 상세 푸터의 `삭제…`이며 상태별 확인 문구를 거칩니다(위 [푸터 액션과 Work 삭제](#푸터-액션과-work-삭제) 참고).

### `GET /api/works/inbox`

미배정·비무시 세션(`WorkInboxSession[]`)을 최근 활동순으로 반환합니다. `GET /api/sessions`와 동일한 세션 집계(`computeSessionAggregates`)를 공유하므로, 필드를 추가할 땐 라우트가 아니라 그 헬퍼를 고쳐야 합니다.

`relatedSessionIds`는 그 세션의 **계보**(subagent 부모 / 큐 체인 / 이어받은 세션)입니다. `buildSessionChainMap`이 **archive된 카드까지 포함해** 계산하며, 비어 있으면 "계보가 없다"는 뜻입니다(로딩 안 됨이 아님). UI는 이 값으로 `🔗 이어진 세션`을 표시하고 그 Work를 먼저 추천합니다.

### `GET /api/works/:id/completion-preview`

완료 확인 다이얼로그가 읽는 영향 범위(`WorkCompletionPreview`)입니다. 카드 수·상태별 수는 **archive 포함**으로 계산하고(`GET /api/works/:id/sessions`와 같은 월 선택 휴리스틱), 실행 중인 에이전트를 가진 보드 카드를 `runningCardIds`/`runningCardTitles`로 함께 내려줍니다. 순수 계산은 `buildWorkCompletionPreview()`(`src/plugin/works/work-lifecycle.ts`)입니다. 필드별 의미는 [`api-reference.md`](./api-reference.md#get-apiworksidcompletion-preview) 참고.

### `GET /api/works/:id/sessions`

Work 상세 다이얼로그가 읽는 세션 요약(`WorkSessionsResponse`)입니다. 연결된 세션별 제목·카드 수·상태별 수·최초/마지막 시각·카드 id·archive 여부·wiki 문서 경로와 Work 전체 합계를, **라이브 보드 + 월별 archive**로 계산해 내려줍니다.

- 읽을 월은 `/api/timeline`과 같은 `timelineArchiveMonths()`로 고르고 창 시작은 `workCardScanFloor(work)` = `min(startedAt, createdAt, ...linkedAt)`입니다. `store.loadArchives()`(전체 스캔)는 쓰지 않습니다 — wiki/Telegram 경로의 스캔을 건드리지 않기 위한 것이니 이 규칙을 깨지 마세요.
- 순수 계산은 `buildWorkSessionsResponse()`(`src/core/timeline-aggregate.ts`)입니다. Work 상세의 집계 규칙을 웹에 다시 구현하지 마세요.
- `archivedCardCount`(세션별 + Work 합계)는 **[재개](#재개-post-apiworksidreopen) 확인 문구가 "카드 N장 복원"을 말하기 위한 값**입니다. 같은 월별 읽기를 두 번 하지 않으려고 새 라우트 대신 이 집계에 붙였습니다. 세션의 `archived`(= 그 세션 카드가 전부 archive)는 이 카운트에서 파생됩니다.
- 필드별 의미는 [`api-reference.md`](./api-reference.md)를 참고하세요.

### `POST /api/works/:id/sessions`

세션을 Work에 연결합니다.

```json
{ "sessionId": "claude-abc123", "projectDir": "/Users/me/workspace/agent-kanban", "role": "review" }
```

- `sessionId` (required) — 이미 다른 Work에 붙어 있으면 `409`
- `role` — `dev` | `review` | `debug` (선택)
- 연결 후 Work의 `startedAt`을 재계산합니다 — 규칙과 공유 함수는 위 [날짜 규칙](#날짜-규칙--startedat은-항상-min)을 참고하세요. 첫 연결만의 특례가 아니라 모든 연결에 적용됩니다.

### `POST /api/works/:id/sessions/batch`

다중 선택 배정의 동사입니다. 위 엔드포인트와 규칙은 같고, 요청 하나가 카드 스냅샷 하나를 모든 링크와 subagent 트리 계산에 공유합니다.

```json
{ "sessions": [{ "sessionId": "claude-a" }, { "sessionId": "claude-b" }], "role": "dev" }
```

응답은 `WorkBatchAddSessionsResponse`(`work`, `linkedSessionIds`, `cascadedSessionIds`, `failed[]`)이며 **부분 성공이 정상 결과**입니다. 필드별 의미는 [`api-reference.md`](./api-reference.md#post-apiworksidsessionsbatch) 참고.

### `PATCH /api/works/sessions/:sessionId`

세션의 링크를 다른 Work로 **옮깁니다**. `POST /api/works/:id/sessions`의 재연결 `409`는 그대로 유지되며, 이동은 링크를 새로 만드는 게 아니라 부모를 바꾸는 것이므로 별도 동사를 갖습니다.

```json
{ "toWorkId": "AbC123", "role": "review" }
```

- `toWorkId` (required) — 없거나 공백이면 `400`, 존재하지 않으면 `404`
- `role` (선택) — 생략하면 기존 링크의 역할을 유지
- 어느 Work에도 붙어 있지 않은 세션(= Inbox)은 `404`
- **게이트: 원본·대상 양쪽 모두 `archivedAt`이 없고 `status !== 'done'`이어야 합니다.** 이미 일괄 archive된 Work의 카드는 wiki 파이프라인으로 넘어갔으므로 그 그룹핑을 되돌리지 않습니다. `done`인데 `archivedAt`이 없는 Work(확인 보류 상태)도 거부합니다 — 곧 실행될 archive와 경합하기 때문입니다. `active ↔ active`, `discarded → active`는 허용. 위반 시 Work 제목이 포함된 `409`
- 이동 대화상자가 열려 있는 동안 상태가 바뀔 수 있으므로(Works 폴링 10초) 게이트는 UI 필터가 아니라 **서버가 다시 검사**합니다

응답은 `MoveWorkSessionResponse`입니다.

```json
{ "from": { "id": "...", "startedAt": "..." }, "to": { "id": "...", "startedAt": "..." } }
```

링크 이동 → 양쪽 `startedAt` 재계산 → 비워진 원본 삭제까지가 **하나의 dual lock 트랜잭션**입니다. 마지막 세션이 빠져나가 원본에 링크가 하나도 남지 않으면 그것은 합병이므로 원본 Work를 삭제하고 `from`은 `null`이 됩니다(세션 없는 Work는 Timeline에 빈 바로만 남기 때문). 이미 대상 Work에 속한 세션을 다시 이동시키면 역할만 갱신하는 무해한 no-op입니다.

### `DELETE /api/works/:id/sessions/:sessionId`

연결을 끊습니다. 해당 세션은 다시 Inbox에 나타나고 `startedAt`은 남은 링크로 재계산됩니다.

- **그 Work가 갖고 있지 않은 세션이면 아무것도 쓰지 않습니다**(no-op). 재계산도 `updatedAt` 갱신도 없습니다 — 예전에는 no-op에서도 재계산해서 손으로 맞춘 날짜를 파생값으로 되돌렸습니다.
- 실패는 서버의 원래 이유를 그대로 돌려줍니다(다른 Works 라우트와 동일).

### `POST /api/works/:id/prune-sessions`

`cardsMissingAt`이 찍힌 링크를 전부 끊습니다 — 아래 [카드가 사라진 세션 링크](#카드가-사라진-세션-링크-cardsmissingat) 참고.

### `POST /api/works/reconcile-links`

모든 Work의 링크에 `cardsMissingAt`을 찍거나 지우는 1회성 보정입니다. 멱등이고 서버 부팅 시에도 한 번 자동 실행됩니다.

### `POST /api/works/ignore-session`

세션을 Inbox에서 영구히 감춥니다(`{ "sessionId": "..." }` → `{ "ignoredSessionIds": [...] }`). 새로고침 후에도 유지됩니다.

### `POST /api/works/:id/summary`

연결된 모든 세션의 트랜스크립트를 모아 `works.summary_model` LLM으로 3~5줄 한국어 Summary를 생성하고 Work에 저장합니다. 완료된 Work의 카드는 이미 archive됐을 수 있으므로 archive된 카드까지 조회합니다.

응답은 `WorkSummaryResponse`(`work`, `summary`, `generatedSessions`, `skippedSessions`)입니다. 트랜스크립트를 하나도 못 읽으면 `422`.

### `GET` / `POST /api/works/config`

Works 설정 조회/저장. `GET`은 `WorksConfigDto`(설정값 + `configured` + 파생된 `route`)를 반환합니다. `POST`는 `WorksConfigInput`의 제공된 필드만 저장하며, 검증 실패는 `400`입니다(`summaryLines`는 3·4·5만, `staleDays`는 1 이상의 숫자, boolean 키는 boolean만).

> 라우트 순서 주의: `/api/works/config`는 `/api/works/:id` catch-all보다 **앞에** 있어야 합니다. 그렇지 않으면 `id`가 `"config"`로 잡힙니다.

## 설정 키 (`works.*`)

공유 settings store에 저장됩니다. 정의는 `src/plugin/works/works-config.ts`.

| 키 | 기본값 | 의미 |
|----|--------|------|
| `works.summary_model` | `DEFAULT_CLAUDE_MODEL` | Summary 생성 모델. `gpt-*` 접두사면 codex 경로, 그 외는 claude 경로로 라우팅. 선택 목록은 `src/core/runtime-config.ts`의 `CLAUDE_MODELS` / `CODEX_MODELS`에서 옵니다 — 설정 패널이 자체 목록을 들고 있지 않습니다 |
| `works.summary_lines` | `4` | Summary 줄 수 (`3` \| `4` \| `5`) |
| `works.assign_prefer_same_dir` | `true` | 배정 추천에서 같은 `projectDir`의 Work를 우선. 끄면 계보 → 최근 활동순만 남습니다(`recommendWorksForSession(…, { preferSameDir })`). `같은 디렉토리` 마크는 **끄더라도 그대로** 붙습니다 — 그 마크는 Work를 설명하는 것이고 이 설정은 정렬에 쓸지만 정합니다 |
| `works.assign_suggest_resume_chain` | `true` | 이어붙인 세션 체인(`relatedSessionIds`)을 추천에 반영 — `🔗 이어진 세션` 배지 + 계보 우선 정렬. 끄면 계보를 계산하지 않습니다 |
| `works.stale_days` | `5` | active Work에 `⚠ 미완료` 경고를 붙이는 경과일 임계값 |
| `works.done_confirm` | `true` | 완료/폐기 시 확인 다이얼로그를 거칩니다. 끄면 클릭이 곧 실행입니다 — 기본값이 `false`였을 때 목록 카드의 초록 primary 버튼 한 번이 산하 카드 전부를 확인·되돌리기 없이 archive했습니다 |

`works.*`는 wiki의 LLM 설정(`wiki.*`)과 완전히 분리되어 있습니다. Summary 모델을 바꿔도 wiki 파이프라인에는 영향이 없습니다.

**설정 패널(`WorksConfigPanel`)의 문구는 이 표의 키를 쓰지 않습니다.** 라벨이 `works.summary_model`·`projectDir`·`resumeSessionId`였던 시절에는 화면이 저장 위치를 설명하고 있었고, 소스를 읽지 않은 사람에게는 아무 뜻이 없었습니다. 키가 필요한 사람은 이 표를 보면 되고, 화면은 동작을 말합니다 — 예: `works.assign_suggest_resume_chain` → "이어서 실행한 세션(이어하기 · 하위 에이전트 · 큐)이면 그 Work를 먼저 추천"(계보는 resume 하나가 아니라 세 가지를 덮으므로 라벨도 세 가지를 말합니다). `WorksConfigPanel.test.tsx`가 이 규칙을 지킵니다.

폼은 **편집 중에는 서버 값으로 덮이지 않습니다.** Works 탭은 10초마다 폴링하며 매번 새 `WorksConfigDto` 객체를 넘기므로, 예전의 `useEffect([config]) → setState(config)`는 사용자가 고치는 중인 값을 10초마다 되돌렸습니다. 지금은 폼이 seed된 값(baseline)과 다르면 dirty로 보고 그대로 둡니다(`resyncForm`).

## 데이터 저장

`~/.agent-kanban/works.json` (`WorkStoreState`). 다른 도메인 store와 같은 규약을 따릅니다 — temp 파일 rename 기반 atomic write + in-process mutex와 `FileLock`의 이중 락. `ignoredSessionIds`도 같은 파일에 함께 저장됩니다.
