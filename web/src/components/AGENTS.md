# components

## Purpose
React SPA component tree for the agent-kanban web UI. Owns all presentational and stateful UI for the board, card detail/create dialogs, capability (skill/MCP/script) management, scheduler, settings, and the wiki knowledge base. Every domain has its own subdirectory with a matching `.css` file; shared cross-domain primitives live in `shared/`. `App.tsx` (one level up) owns tab/modal state and wires these components to hooks.

## Key Files
This directory itself contains no files — see Subdirectories below.

Its columns are **days** and its smallest row is a **session**: a day is the floor because half this board's cards finish in under three minutes, and a session is the floor because every card belongs to one, so cards render as day blocks inside their session's row rather than as rows of their own. Cards appear only from the moment they actually executed (`startedAt`/`completedAt`), never from `createdAt`, and there are no scheduled/ghost bars. Rows nest **directory → Work → session**, with a Work grouped by its own `projectDir` (else its sessions' majority) so one Work never splits across two groups; unassigned sessions *are* shown, marked 미배정 after the Works of their directory, and the row's `배정` button reuses the assign-all modal with a single session. Subagents are hidden by default (`kanban-timeline-subagents`). Grouping/bucketing is pure in `timelineRows.ts` and date geometry is pure in `timelineModel.ts` — `TimelineView` renders and handles pointers only. Rows render through four `React.memo` components (`DirRowView` / `WorkRowView` / `SessionRowView` / `RowCells`) sharing **one referentially stable `TimelineHandlers` bundle**, and the live drag lives in a ref with only `{ workId, preview }` in state: that is a performance contract, not a style. `setDrag` used to re-render the whole view on every `pointermove` with no memoized child anywhere, repainting the month view's 35 columns × ~60 rows, and `measureColumns` ran two `querySelector`s plus two forced layouts per move — column geometry is now measured once at `beginDrag` into `metricsRef` (the columns cannot move mid-drag: a range change aborts it and a captured pointer does not scroll). `App` hands down fresh inline arrows every render, so callback props reach the bundle through a `latest` ref; put new callbacks **in the bundle**. The bar's edge handles carry both a drawn column and a **raw** one: `TimelineBar.rawStartIndex`/`rawEndIndex` may be negative or past the last column, rendering uses the clamped `startIndex`/`endIndex`, and **editing uses raw** — a `→` on a Work that started 8/20 viewed in the 9/1 week has to write 8/21, where the clamped read wrote 9/2 and destroyed nearly two weeks with no undo (the inversion guard and `aria-valuenow`/`aria-valuetext` are raw too; a *drag* keeps using the visible column the user dropped on, compared against the drag origin so a press without a drag still writes nothing). `beginDrag` calls `focus()` explicitly after `preventDefault()`, which pointer capture requires and which also kills the implicit focus a `tabIndex` element would get — the documented keyboard edit was Tab-only, and `→` right after clicking a handle moved focus to the 월간 button. Every date edit leaves an undo through `onNotify` (the `App`-owned `WorkSessionNotice`), since nothing confirms it. A terminal Work's bar **never falls back to `updatedAt`** for its end (a title edit grew a finished bar by a day); a missing `resolvedAt` draws to today instead, and the `폐기` note follows the same rule. The legend is derived, not fixed: `timelineLegend(rows)` lists only what is drawn — the old six-item constant permanently advertised a `대기` swatch a grid of *executed* work almost never contains — and labels come from `TIMELINE_STATUS_LABELS`, Korean throughout, with `complete` read as `검토 대기` because its board hue is a pink-red that reads as *failed* (the colour belongs to the board; the label carries the meaning). The view has its own directory filter (`timelineDirOptions` + `filterTimelineRows`, keyed on `TimelineDirRow.groupKey` — never re-derive it by slicing `'dir:'` off `key`): `BoardProjectSwitcher` is hidden here because it filters card columns, which left a busy grid with no filter but per-group collapsing, and the options come from the grid's own rows so a project whose cards are all archived is still filterable. Options are computed **before** the filter is applied, or selecting one directory erases every other option. The five-line footnote is now a first-run block behind a `?` toggle (`kanban-timeline-help-seen`), and a failed window dims the grid (`.timeline--errored`) and rewrites the empty state — a raw `Not found` over a session-free grid read as "nothing ran this week", so `describeTimelineError` turns it into a sentence. Sessions come from `useTimeline` (its own windowed `/api/timeline`, because the grid needs archived cards); the Works come from the shared `useWorks` list, and session → Work mapping happens client-side so an optimistic assignment re-groups instantly. Colour is split across four axes (directory palette / ink Work bar / violet session rail / card status hues) — see `docs/design-system.md`; never give the Work bar a status hue or the rail a directory colour. It is a plain CSS grid, no chart or calendar library. A Work's dates are editable two ways — dragging a bar's edge handle, or the detail dialog's date inputs — and both call the same `useWorks.updateWorkDates`. Both edges move on every Work: an open Work's right edge sets a *planned* end that survives completion. Grid placement lives on `.tl-bar-slot` (the wrapper), not `.tl-bar`, because the bar is a `<button>` that cannot nest the handles; drags use the handle's own pointer capture, ending on `lostpointercapture` only. The `Work` label column is user-resizable: the `.tl-label-resizer` grip on the header's right edge drags (or nudges with ←/→, resets on double-click/Home) `--tl-label-width`, set inline on `.timeline` from state clamped by `clampLabelWidth()` and persisted under `kanban-timeline-label-width` — width is measured from the sticky header label cell, not the grid, so it is correct while the month view is scrolled. `WorkDetailDialog` is one vertical stack (상태 배지 → 기본 정보 → Summary → 기간 → 산출물 → 세션) — add a full-width row, do not reintroduce the old right-hand panel column that duplicated session info. **Say each fact once.** The status badge is the only one (`describeWorkStatusBadge`: `진행 중 · 3일째` open, `완료 · 3일 소요` terminal), and the 기간 row no longer repeats the day count it used to print as `3일째 active` — one field in two languages. Nothing in the dialog names a wire enum: `WORK_STATUS_LABELS` replaced the literal `ACTIVE` that sat beside `완료`/`폐기`, and the 산출물 chips come from `describeWorkArtifacts` (`카드` / `끝난 카드` / `남은 카드` with the covered statuses in the tooltip) because the old `done 5` / `in_progress 1` were the enums *and* the second one mis-named its own number — `inProgressCount` is `todo + in_progress`. `기본 정보` edits the title and `projectDir` inline through `useWorks.updateWorkMeta` (Enter commits, Escape abandons, blur commits): a Work is created from a session's first prompt, so its title was whatever that prompt happened to say, forever. The `메모` panel below Summary is the Work's one **human-owned** field (`Work.notes`, capped at `WORK_NOTES_MAX_LENGTH`) and is deliberately styled *unlike* the Summary hero — plain `.work-detail-row` chrome, no hero background — because the difference between them is who writes the field: Summary is regenerated from transcripts and overwritten wholesale by `↻ 다시 생성`, so anything typed there is lost. It uses the same draft-sentinel rule (the 10s poll cannot clobber in-progress typing) but commits on an **explicit button**, not blur: a multi-line note is long enough that clicking away mid-thought is normal, and it keeps the draft on a failed PATCH rather than reverting to the server's copy. Unsaved notes show a badge and gate every close path (Escape / ✕ / backdrop) behind a confirm, since a discarded note is recoverable from nowhere. Two traps there, both load-bearing — Escape must `stopPropagation()` (`DialogSkeleton` reads it as "close the dialog"), and the drafts are mirrored in a **ref** that every handler reads, because `input.blur()` inside a `keydown` handler fires `onBlur` *synchronously* before the re-render, so a state-only implementation had Escape clear the draft and the blur immediately commit the text Escape had just thrown away. A session row's date is its **first card's** instant (`WorkSessionSummary.firstCardAt`), not `linkedAt` — every session in a Work triaged this afternoon read as today. A row whose session has lost **every** card is marked from `WorkSessionSummary.cardsMissingAt` (`.work-session-item--missing`, warn colours, a sentence explaining that the link is dragging the Work's start back to its 연결 time) and the footer grows `🧹 끊긴 세션 정리 (N)` → `useWorks.pruneWorkSessions`. Read the stamp, **never `cardCount === 0`**: this dialog's counts come from a month-bounded archive read, so "no cards in the window" and "no cards at all" are different answers and only the server knows the second. The cleanup confirms (a card-less session does not return to the Inbox, so this is the one link removal with no way back) and reports its failure next to its own button rather than only in the shared banner, since the footer is far from the top of the dialog. **No permanently disabled controls.** `＋ 세션 연결` (App never passed a handler) and `📚 Wiki 정리` (hardcoded `disabled`) are gone rather than parked: a button that can never fire advertises a capability and withholds it, and linking a session already has a working home in Inbox triage or `⋯ → 다른 Work로 이동`. `요약 생성` is `kv2-btn--outline`, not primary — it spends an LLM call and was the strongest-looking target on a dialog whose job is reading a Work. Its 산출물 numbers and session titles come from `useWorkSessions` (`GET /api/works/:id/sessions`), **not** from the `cards` prop: completing a Work archives every card under it, so a board-derived rollup showed `카드 0 · done 0` and fell back to raw session ids for exactly the Works the dialog exists to review. `work.sessionLinks` still decides which rows render (an optimistic unlink must be instant); the response only supplies each row's numbers, and a missing/failed response falls back to board cards *visibly* rather than silently reporting zero. A resolved (`done`/`discarded`) Work reads as a finished record: the `✅ 완료 시: …` notice is hidden, `폐기…` is disabled, and the span is pinned to `resolvedAt − startedAt` via the pure `workAgeDays()` — an `active` Work's planned end is a forecast, so it still counts to today. `wiki 문서` has three states (kept doc paths / `생성 대기 중` when a card is still `wiki.status='pending'` / `없음`), never the old unconditional `아직 없음`. The `대화` button and Timeline day cells go through `App`'s `handleOpenCardById` / `handleOpenWorkSession`, which fall back to archive-inclusive reads (`fetchCard(..., { includeArchived: true })`, `fetchSessionCards`) and report failures through `showError` — a bare `void` call there left the click dead with an unhandled rejection. Session-level actions live in the `⋯` overflow menu on each linked-session row (`WorkSessionMenu`, one popover — the role group expands in place rather than flying out; `role="menu"` is honoured with first-item focus on open, ↑/↓/Home/End, `role="menuitem"` on the 역할 변경 toggle, and an `Escape` that `stopPropagation()`s so it closes the menu and not the detail dialog behind it), and `MoveSessionDialog` **reuses `WorkAssignInline`** rather than adding a second "where does this session belong" picker: it only adds a `현재:` line, excludes the current Work from the ranking, swaps the left footer action, and renders an impact preview computed with the server's own `resolveWorkStartedAt`. It is nested inside the detail dialog rather than portalled out of it, and `DialogSkeleton` already stops Escape on its own `.kv2-dialog`, so only the inner dialog closes. Do **not** read that as a focus trap: `useModalAccessibility` listens on `window` in the *bubble* phase and `DialogSkeleton`'s `onKeyDown` `stopPropagation()`s every non-Escape key, so Tab never reaches the trap for **any** dialog — `BulkAssignModal` registers its own shortcuts with `capture: true` precisely because of this. Moving the trap to the capture phase is an app-wide change, not a Works one. `WorkMergeDialog` (`⇉ 다른 Work에 병합…`, active Works only) is shaped after it on purpose — same target list, same "state the consequences above the confirm button" preview (`describeWorkMergeImpact`, which runs the server's own `resolveWorkStartedAt` over the post-merge link set), same keep-the-dialog-open-on-rejection error handling — but its unit is the whole Work. Targets come from `mergeTargetsFor` and are **`active` only**, because the store's move gate refuses both ends of a closed Work and offering one would be a `409` after the click. On success `App` moves the open dialog to the *target* (`setOpenWorkId(result.to.id)`); the source survives as `discarded`/`superseded`, so the Resolved row says 병합됨 rather than 폐기 (`resolvedWordFor`) — never reuse the 폐기 wording for a merge source, its sessions are alive somewhere else. The result toast (`WorkSessionNotice`) is owned by `App`, not the dialog, because a move that empties the source Work deletes it and unmounts that dialog; an undo is offered only when the action is actually reversible. `폐기…` and `✔ 완료 (일괄 archive)` are *requests*, not actions: both open `WorkResolveConfirmDialog` (one `DialogSkeleton` shared with the Works list row's `완료…`, which is a **ghost** button rather than the green primary it used to be — the most destructive action on a row people click to open 상세 must not be its most inviting target). The completion mode reads `GET /api/works/:id/completion-preview` through `useWorkCompletionPreview` and keeps its confirm button disabled until the scope lands, refusing outright while a card still has a live agent run (`runningCardIds`; the server re-checks with `409`); its copy is pure (`describeWorkCompletion` / `describeCompletionByStatus` / `describeKeptFavorites` / `describeWorkCompletionBlock` / `describeWorkDiscard` in `worksAssign.ts`). It also names the cards the sweep will **not** take: favorited board cards stay put, so `favoriteCardIds` is counted out of `sweepCardCount` and reported as `⭐ 즐겨찾기 카드 N장은 보드에 그대로 남습니다` — the headline's number and the board afterwards have to agree. A **third mode, `reopen`**, shares it: `↺ 다시 열기…` replaces the merge button on a resolved Work and goes through the same gate, because reopening moves a pile of cards between the archive and the board and `window.confirm` cannot say how many. Its count comes from `detail.archivedCardCount` (`GET /api/works/:id/sessions`, which the dialog already holds) — **not** a new route, and `null` renders as "확인하지 못했습니다" rather than an invented number, with the action still enabled since a restore is not destructive. `describeWorkReopen` also has to keep saying the cards come back **`done`**: the sweep recorded their previous statuses nowhere. Reopen is the one mode where the detail dialog **stays open** on `'done'` (the point is to keep working on the Work), so `handleResolved` branches on the mode rather than closing unconditionally. Its title is `완료 확인` / `폐기 확인` / `다시 열기 확인` with the Work named in the body — embedding the Work title would make `getByRole('dialog', { name })`, which matches substrings, resolve to two open dialogs. The detail dialog closes only when the hook answers `'done'`; the old `onComplete(id).then(() => onClose())` closed on a *cancelled* confirmation and read as a finished archive. The footer's left edge is the destructive zone (`kv2-actions-danger`), least severe first: `폐기…` then `삭제…`. Delete is the only UI entry point for `DELETE /api/works/:id`, is never skipped past a confirmation (unlike move/unlink, it has no undo), and its status-branched copy lives in the pure `confirmDeleteWorkMessage()` — a `done` Work's prompt must keep saying that archived cards and wiki documents are not restored. Inbox triage is batchable: dragging vertically over the rows selects the range and reveals checkboxes, after which clicking a row toggles it, and the action bar under the list assigns the whole selection to one Work. That bar renders **below** the rows because mounting it above would push every row down under the pointer as a drag starts, and pointer capture is taken on the first move past the 4px threshold — **not** on press, since a captured pointer redirects the trailing `click` to the capture element and the row toggle would silently die. Selection geometry is row-snapped hit-testing in `worksAssign.ts` (`rowIndexAtPointer` / `sessionIdsBetween`) with no rubber-band rectangle to draw — snapping to rows makes the band redundant with the checkboxes and the row tint — anchored by `sessionId` so an Inbox poll cannot move the anchor, and re-measured every move. The batch reuses `WorkAssignInline` through `mergeSessionsForAssign` (oldest session as the representative; `projectDir` only survives a single-directory batch) — the `bulk` prop changes copy only, never the ranking. Links go out as **one** `POST /api/works/:id/sessions/batch` (the per-session loop it replaced re-read the whole card archive server-side once per session), and partial success is still a normal outcome — now as the server's own `failed[]`: those sessions stay selected for a retry **and each failed row shows its own reason** (`⚠ 배정 실패 — …`), which the one-sentence shared banner could not. The batch panel `scrollIntoView({ block: 'nearest' })`s when it opens (it must render below the rows, so on a long Inbox it opened off-screen) and lists the selection as chips, since the panel body only shows the representative session. While selecting, the rows' own actions (`배정` / `대화 보기` / `폐기`) are hidden and any open single-row panel closes — the row *is* the toggle, and those three buttons were both mis-click targets and drag-surface obstructions. A selection-mode row is a real toggle button (`role="button"`, `tabIndex`, `aria-pressed`, Enter/Space). All three 선택 해제/끝내기 buttons call one `clearSelection()`, and pruning the selection to empty also closes the batch panel — `bulkPanelOpen` used to survive, so the next row checked re-opened a panel nobody asked for. The Active list has its own search / directory filter / sort toolbar between the heading and the rows (Inbox and Resolved are unaffected). The rule is the pure `selectWorks()` in **`src/core/work-list.ts`** — the same function `GET /api/works` applies — and the narrowing happens client-side anyway because the Works poll must fetch the *whole* list (the Timeline grouping, the assign recommendations and the move dialog all read every Work), so never re-implement the ordering here and never narrow the request. Sort labels come from `WORK_LIST_SORT_LABELS`; `오래 방치된 순` is the exact mirror of the old fixed `updatedAt`-descending order, which sank a three-week-untouched Work to where it was already invisible. A narrowed heading reports `2 / 3개` and an empty result says `검색·필터 조건에 맞는 Work가 없습니다` rather than the "no active Works" copy — an empty tab and an empty search are different situations. A planned end that has passed is marked from the shared `workPlanOverrunDays` via `describeWorkPlanOverrun`: a `예정 N일 초과` chip on the list row and the detail 기간 row, plus `.works-card--overrun` (the row's accent stripe turns warn, which is what makes a late Work findable by scrolling) and `.tl-bar--overrun` on the Timeline bar, whose geometry cannot say it — the bar stops at the planned date whether that date is next week or three weeks ago. `--kv2-warn-*`, not danger: nothing is broken, the plan is just older than the work. Keep it separate from `⚠ N일째 미완료` (`works.stale_days`) — different complaints, both can be true. Resolved is count-first — collapsed by default with `전체 N개`, no date window — so `resolvedWorksNewestFirst` decides its order. Both assign surfaces (the assign-all modal and the inline panel) render **the selected option's own inputs directly under that option** — the modal's option list is therefore an `aria-pressed` toggle group, not a `role="listbox"`, because a listbox may only contain options; the sticky `.kv2-dialog-footer` keeps submit in view. The inline panel's recommendation list follows the same rule (`role="group"` + `aria-pressed` buttons, never `role="option"` buttons, which get neither the button's keyboard behaviour nor a listbox's), and its field ids come from `useId()` — the panel can render three times at once (Inbox row, batch panel, move dialog) and the old fixed `works-new-title`/`works-new-role` ids collided the moment two were open, pointing a `<label>` at the wrong control (e2e addresses them by label, not id). All three assign surfaces put 무시/폐기 in the footer's **left `kv2-actions-danger` zone** with `kv2-btn--subtle-danger`: the inline panel used to sit it as a right-hand ghost next to the primary 연결, so one irreversible action had three different weights across three screens and lived next to the confirm button on one of them. 취소 joins that same left group rather than taking `kv2-action-cancel`, because a button between two `auto` margins floats mid-footer. `MoveSessionDialog`'s `⤺ Inbox로 되돌리기` takes the same slot with `tone: 'neutral'` (`kv2-btn--outline`) — it is not destructive. `WorkAssignInline`'s submit is gated on the resolved `selectedWork`, **not** the held `selectedWorkId`: the recommendation list is rebuilt every poll, so a target that completed under an open panel left 연결 enabled and POSTed a session onto a finished Work (the server now also answers `409`). The modal's single-key shortcuts route through the pure `resolveBulkAssignShortcut` — `Enter` on a `<button>`/`<a>`/`contenteditable` belongs to that element (it used to run 연결하고 다음 *and* `preventDefault` the focused `X 폐기`), and `INPUT`/`TEXTAREA`/**`SELECT`**/`contenteditable` swallow every non-Enter key (`x` with the 역할 select focused discarded the session). Its `n / N` counter sits in a `role="status" aria-live="polite"` region beside the live `describeBulkAssignProgress` tally, and its session header carries 대화 보기 like the Inbox row does. They also share one affinity vocabulary via `WorkAffinityMarks.tsx` (`DirChip` / `WorkAffinityMarks`): a hashed per-`projectDir` colour from `worksAffinity.ts` published by `.works-dir-c{n}` as **two** variables — `--works-dir-accent` (swatch: bars, tints) and `--works-dir-text` (letters) — plus `🔗 이어진 세션` for session lineage in a hue no directory slot uses. Never a colour literal and never `--kv2-dir-{n}` directly in component CSS. **The chip tints the directory name; there is no dot.** A 10px dot is the smallest possible sample of a hue and it was carrying the whole "which project is this" signal, at a size where two neighbouring slots are the same dot; `.works-dir-dot` survives only in the Timeline label, where the row already has a full-height colour band. **Letters use `--works-dir-text`, not the swatch** — painting them in the raw accent left `--kv2-dir-2` at 3.7:1 on light and `--kv2-affinity-chain` at 3.1:1 on dark, and no single swatch value can satisfy both themes; the palette's two axes (45° hue ring + alternating luminance) and the AA guards live in `docs/design-system.md`, `worksAffinity.test.ts` and `styles/token-contrast.test.ts`. Lineage comes from the server's `relatedSessionIds` (archived cards included) and outranks a shared directory in `recommendWorksForSession`'s optional 4th argument; omitting that argument must keep the plain same-dir-first order, which the move dialog relies on. Its 5th argument is the options bag carrying `preferSameDir` (`works.assign_prefer_same_dir`): `false` drops the same-directory *group* from the ranking but still reports `sameDirectory`, because the 같은 디렉토리 mark describes the Work and the setting only decides whether that fact sorts. Wire it from `config` at every Inbox surface (`InboxRow`, the batch panel, `BulkAssignModal`) — the setting was written by the settings panel and read by nothing, so the checkbox was decorative for its whole life. The Inbox **row** now carries both triage signals itself rather than hiding them behind 배정: a 상태 칩 from the pure `describeSessionState()` (`subagent` outranks `실행 중` outranks `미실행`, and a settled `complete`/`done` session gets **no** chip so the common row stays quiet) and a `🔗` mark (`이어진 Work N` when some Work already holds the lineage, else `이어진 세션 N`), both gated off together by `works.assign_suggest_resume_chain`. The header reads `· 최근 활동순` because that is what the sort is — it claimed `· 오래된 것부터` over a `updatedAt`-descending list. Rows the server no longer returns at all: sessions with no card, subagents whose parent is already assigned, and anything past the Inbox's `since`/`limit` window. The header's `🗑 무시한 세션 N개` opens `IgnoredSessionsPanel`, the recovery path for 폐기 (`GET /api/works/ignored-sessions` + `DELETE /api/works/ignore-session/:sessionId`): the ignore list was append-only and unreadable, so a click on a row — or one mistyped `x` in the modal — erased a session from every screen for good. ## For AI Agents
### Working In This Directory
- **MUST READ before adding or changing any UI: [`docs/design-system.md`](../../../docs/design-system.md).** Board cards and the Card Detail dialog define the look; every screen reuses the kv2 primitives (`kv2-btn`, `kv2-input`, `kv2-badge`, …) and `Card/DialogSkeleton.tsx` for modals. No local overrides of `kv2-*` primitives, no hand-rolled modal overlays.
- Never fork DTOs — all shared types come from `src/core/types.ts` (imported via the `../../../../src/core/types` relative path from most component files).
- `fetch()` calls belong in `web/src/hooks/*`, not in components. Components receive data/handlers as props or call hook-exported functions (e.g. `useScopeInventory`, `useSkillsApi`).
- Each domain directory owns at most one `.css` file containing **layout only** (grid/flex/gap) plus domain badge/status variants; colors, typography, and control looks come from kv2 tokens/primitives. No CSS-in-JS, no Tailwind.
- Modals use `Card/DialogSkeleton.tsx` (overlay/backdrop/dialog structure, `useModalAccessibility` focus trap + Escape, optional size persistence). Do not build a bespoke overlay.
- Resizable dialogs use `usePersistedDialogSize(storageKey, ref, defaultSize)` to remember width/height in localStorage.
- **Reusing a primitive built for a different container needs a variant, not a local override.** `.kv2-meta-dropdown` is sized for a card-sidebar meta *field* (`width: 100%; flex: 1`). Dropping it into a dense row and overriding only `flex` locally leaves the `width: 100%` as its flex base size, so it claims the whole row and every sibling with `min-width: 0` shrinks to `0px` — the Work detail's session rows lost their title entirely this way. Compact triggers must add `kv2-meta-dropdown--inline` (`width: auto; flex: none`); a trigger inside a dialog also passes `useAnchoredPopover(w, { boundarySelector: '.kv2-dialog' })` so the popover flips up instead of hanging past the dialog's bottom edge.
- **Footer actions follow `kv2-actions-split` everywhere, including panels that are not dialogs.** 취소/Close takes `kv2-action-cancel` on the left, forward actions group in `kv2-actions-primary` on the right with the primary last, and destructive actions go left in `kv2-actions-danger`. A footer must never leave a button *between* two `auto` margins (`kv2-action-cancel` and `kv2-actions-primary` both set one) — it ends up floating mid-footer, which is how `BulkAssignModal`'s 폐기 drifted to the centre. A local footer class combined with the primitive may set spacing only: no `justify-content`, no per-button margins.
- **Single-key shortcuts inside a `DialogSkeleton` must bind on `window` in the capture phase** (`addEventListener('keydown', fn, true)`), not via an `onKeyDown` prop on an inner element. `DialogSkeleton` calls `stopPropagation()` on every non-Escape key, and React's synthetic `stopPropagation` forwards to the native event at the React root — so a bubble-phase listener never fires, and a subtree `onKeyDown` only fires when focus happens to sit inside that subtree (DialogSkeleton's initial focus can legitimately land on the dialog's × button). `Works/BulkAssignModal.tsx` is the reference implementation; leave Escape to `useModalAccessibility`.
- Quick Action Add/Edit stays separate from the side-sheet runner. The collapsed desktop launcher is a labeled `⚡ Quick ›` edge tab positioned in the Board's left gutter without consuming layout width; mobile shows the same horizontal tab above the Board. The expanded `DialogSkeleton` overlays from the left, dims/inerts Board/List without changing geometry, and becomes full viewport on mobile. The runner unmounts while Add/Edit is open so modal focus traps do not overlap. A new Prompt draft uses `useRuntimeDefaults().prefs.runtime ?? "opencode"` and `useRuntimeModelSelection().getDefaultModelForRuntime()`; saved edits win, and asynchronous defaults must respect per-field Runtime/Model touched state.

### Testing Requirements
- Bun test runner (`bun:test`), colocated as `ComponentName.test.tsx` / `.test.ts` next to the component (see `Board/`, `Card/`).
- Prefer testing extracted pure functions/selectors (e.g. `board-selectors.ts`, `board-utils.ts`, `confirmBoardCardDelete`) over full component rendering.
- There is no DOM in this test setup — component tests use `renderToStaticMarkup` from `react-dom/server` and assert over the HTML string. That is enough for **copy guards** (`WorksConfigPanel.test.tsx` asserts no setting key or wire field appears in the settings panel) but not for interaction; extract the rule as a pure function instead (`resyncForm`, `describeWorkStatusBadge`, `describeWorkArtifacts`) and cover the interaction in `e2e/`.
- `Works/worksAffinity.test.ts` reads `styles/kanban-v2.tokens.css` directly via `styles/tokenColor.ts` and enforces the palette's hue spacing plus the existence of a `-text` twin per slot. A new directory colour therefore needs three edits together — `--kv2-dir-{n}`, `--kv2-dir-{n}-text`, `.works-dir-c{n}` — and `DIR_COLOR_SLOTS` raised; miss any one and this file or `styles/token-contrast.test.ts` fails.

### Common Patterns
- View-model selector modules (e.g. `Board/board-selectors.ts`) transform raw `KanbanCard[]` into render-ready shapes, keeping components declarative.
- Polling via `usePolling(refreshFn, intervalMs, enabled?)` is the sync model — no websockets, no React Query/SWR.
- Destructive actions (delete, freeze, remove) confirm via `window.confirm(...)` before calling the hook mutation. **Exception: the three Work status transitions** (완료 / 폐기 / 다시 열기) use `Works/WorkResolveConfirmDialog.tsx`, a `DialogSkeleton` — the completion confirmation has to state how many cards the sweep will archive and refuse while a card still has a running agent, the reopen confirmation has to state how many come back, and `window.confirm` can render none of it. Reuse that component rather than adding a third confirmation pattern.
